## 二、`M1-1` 「记录永不失败」在服务端的精确语义

### 2.1 🔴 服务端不实现这条规则,而这正是它的落法

`U1.1` 推论 1 的原文:「**本地落盘即反馈。** 提交后的那次反馈由本机写入触发,不等任何一次网络往返」;
`U1.1` §三 第一行的后端契约意图逐字写着:「**无契约,且这正是它的性质。有契约就有一次能失败的往返**」。

**所以「记录永不失败」在服务端不是一段代码,是一处刻意的空白。** 服务端能做的只有反过来的一件事:

> **`POST /records` 的任何一种失败响应,都不得被理解为「这条记录不存在」。**

这不是措辞问题,它有一个结构后果:**服务端的写入路径里不许有任何一次回滚**。
一旦有回滚,就存在一个「服务端认为它没发生、而端已经给过用户成功反馈」的状态 —— 那正是 `U1.1` 推论 3 的反面判据。

**现状(已绿),而证据不是「没有 `try`」,是「没有 `delete`」:**

```bash
$ grep -n 'store\.' server/kaodian-domain/src/main/java/com/kaodian/server/collect/CaptureService.java
218:        Touch existing = store.findByClientToken(request.clientToken());
324:        Touch stored = store.append(touch);
```

**整个 `CaptureService` 只碰 store 两次:一次查幂等键,一次追加。没有 `store.delete`** ——
也就是说,`append` 之后没有任何一条路能把它撤掉。**这比「没有 `try/catch`」强,因为回滚不一定长成 `catch` 的样子。**

🔴 **而那唯一的一处 `catch`,恰恰是推论 3 的代码形态,不是它的反例:**

```java
// CaptureService.java:257-265
boolean available = true;
try {
    recognition = VisionTagger.enforceClosedSet(visionTagger.classify(image, mimeType, candidates), candidates);
} catch (RecognitionUnavailableException e) {
    available = false;      // 识别挂了 ≠ 记录挂了
}
// ↓ catch 之后照样往下走到 mountAndAppend —— 失败只改了一个 boolean,没改「这条记录存不存在」
```

`FileTouchStore.append`(:146)先落盘再改内存(:164-165),盘写失败时内存不变 —— 部分成功在结构上不可能。

### 2.2 三档:必须前置的、必须吞掉的、真失败的

| 档 | 是什么 | 端怎么办 | 码 |
|---|---|---|---|
| **A · 必须前置,是真失败** | 这一条请求**结构上不可接受**,重发多少次都一样 | 记录留在本机,给用户「删掉它」或「改一下再传」两条路(`U1.6` §三) | `UNKNOWN_FIELD` `MALFORMED_BODY` `VALIDATION_FAILED` `MISSING_NODE_CODE` `NODE_NOT_IN_SYLLABUS` `INVALID_LIMIT` `INVALID_CURSOR` |
| **B · 必须吞掉,转本地队列** | 服务端这一侧的事,与这条记录的内容无关 | **什么都不用做**,留队列自动重试 | `SERVER_ERROR` `SYLLABUS_DATA_BROKEN` `REQUEST_REJECTED` + 一切超时/断连 |
| **C · 看起来是 A,实际是 B** | 🔴 `401 TOKEN_EXPIRED` | **什么都不用做**,续期后自动重发 | 见 §2.3 |

🔴 **A 档里没有一个码与「这条记录该不该存在」有关。** 它们全部在说「这个请求我读不懂」。
`NODE_NOT_IN_SYLLABUS` 是唯一一个看起来像内容判断的 —— 它不是:骨架树里没有这个 code,是端送来了一个不存在的标识,与「这一笔学习算不算数」无关。
`U1.1` §2.3 允许失败清单第 6 行「挂载到某个考点」失败时「记录在,没挂上」—— **那说的是打标管线(`M2`),不是 `POST /records`**。
`POST /records` 的 `nodeCode` 是**用户自己从树里挑的**,挑了一个不存在的 code 只有一种成因:端的树缓存过期。这是 A 档。

### 2.3 🔴 端要的二分不是 4xx/5xx,是「要不要用户动手」

`U1.6` §三 最后一行逐字要求:「**补传返回 4xx 与 5xx 必须可区分**」,理由是「一个要用户动手,一个用户什么都不用做」。
**但 `401 TOKEN_EXPIRED` 是 4xx,而它要的是「用户什么都不用做」** —— `U1.1` `A-09` 逐字:「令牌过期不许挡住记录,续期是静默的,用户无感」。

**裁定:契约给的是「要不要用户动手」这张表,不是 HTTP 类别。**

| 响应 | 端的动作 | 用户看到 |
|---|---|---|
| `2xx` | 出队,标已同步 | 无 |
| `401 TOKEN_EXPIRED` | **留队**,续期后自动重发 | 无 |
| `401 UNAUTHORIZED` / `403` | **留队**,引导重新登录;登录后自动继续 | 登录门(不是「这条记录失败了」) |
| `401 ACCOUNT_DEACTIVATED` | 🔴 **停止自动重发**,队列**原样留在本机不删** —— 重发永远不会成功,但**记录是用户本机的数据,不替他丢** | 「已注销」门(`U5.5`),不是「这条记录失败了」 |
| 其余 `4xx` | 该条标失败、**保留在本机**,给两条路 | 「这一条传不上去」+ 删掉 / 改一下再传 |
| `5xx` / 超时 / 断连 | 留队,自动重试 | 队列条数 |

**判据 ③(测试):** 一个用例枚举 A 档全部码,断言它们**都不在**端的「留队自动重试」集合里;
再枚举 B 档 + `401`,断言它们**都在**。这张表是端与服务端共有的,写在契约里,不是写在端的实现里。

### 2.5 🔴 `M1-2` `M1-3`:额度耗尽时记录照样成功,落在哪一层

**落在「调用图上没有那条边」这一层,不落在 `try/catch`。**

`CaptureService` 的构造器参数只有 `TouchStore` / `VisionTagger` / `SyllabusSource` / `Clock`(:65)。
额度要在这条路上生效,必须先给它加第五个参数 —— **那是一次会出现在 code review 里的改动,而 `try/catch` 不会**。
这就是「结构挡」与「规则挡」的区别,与 `B0` §12.3 用「端点不表达已同意语义」挡住第三档是同一条推理。

**但有一处上了膛的枪,必须在这里点破:**

```java
// 现状:server/kaodian-domain/src/main/java/com/kaodian/server/collect/TouchKind.java:41
private final boolean consumesAiQuota;      // VOICE/PHOTO=true,其余 false
```

**实测:这个字段今天有 0 个消费者**(`grep -rn 'consumesAiQuota' server --include=*.java` 除 `TouchKind.java` 自身外零命中)。
它挂在 `TouchKind` 上,而 `TouchKind` 是 `Touch` 的字段 —— **也就是说它挂在「记录」上,而不是挂在「调用」上**。

🔴 **裁定:删掉它。** 理由不是「没人用」,是**它说的话是错的**:

- 一条 `PHOTO` 记录,用户自己从树里挑了考点、根本没走 `POST /records/{id}/image` —— 它一次外部模型调用都没有,而这个字段说它有

**「哪一次调用是外部模型调用」由调用点决定,不由记录类型决定。** 而下一个实现额度的人打开 `CaptureService`,
看到 `request.kind().consumesAiQuota()` 触手可及,**扣额度就会被写进记录写入路径** —— 冻结口径 2 当场失守,而且是以一种「代码读起来很合理」的方式。

## 三、`M1-4` `M1-5` `M1-6` 幂等与批量部分成功

### 3.1 键:业务键,不是请求键

`B0` §7.3 的三种键原样执行。M1 的两个写端点用**业务键**:

| 项 | 落法 |
|---|---|
| 键 | body 里的 `clientToken`,端生成 UUIDv4,`@Size(max = 64)`(现状 `Touch.java:48-49`) |
| **生成时点** | 🔴 **端落本地的那一刻,不是发请求的那一刻。** 发请求时生成,重试就会换一个键,幂等当场失效(`U1.6` §2.3) |
| 重复时 | **`200` + 返回上一次的结果,不是 `409`**(`接口契约` §1.5)。现状已实现:`201` 新建 / `200` 幂等重放 |
| 不带 | **允许。** 不带就是不去重,每次都新建 —— 端不带 `clientToken` 是它自己放弃了补传能力,不是一个错误 |
| 🔴 不用 `Idempotency-Key` | **`接口契约` §3.3 那张八行表是唯一真源**,`M1` 的端点一行都不在上面。⚠️ **2026-09-03 更正(KUBI-89 审核轮):本行上一版照抄了 `B0` §7.3 的「三个落点」并自己数了一遍,那个数已作废** —— 一个横切的数被每份文档各存一份,过期是迟早的事,所以本文只留指针 |

### 3.2 🔴 唯一性是 `(userId, clientToken)`,不是 `clientToken` 全局唯一

**现状:`TouchStore.findByClientToken(String clientToken)`(`TouchStore.java:38`)没有 `userId`。**

全局唯一的后果是:A 的补传被 B 的一条记录去重掉,**A 那一条静默消失**,而接口返回 `200`、日志一条没有 —— `R-59` 同构失败。
UUIDv4 跨用户碰撞概率可忽略,**但「可忽略」不是「不可能」**,而这里的代价是丢一条用户手记的记录。
组合唯一让这件事在结构上不可能,成本是索引多一列。

### 3.3 `M1-5` 去重窗口:不设窗口

**裁定:`clientToken` 与记录同生命周期,不设过期窗口。**

| 候选 | 代价 |
|---|---|
| 设 N 天窗口 | 🔴 离线超过 N 天的一批记录补传时会**产生第二条**。而 `U1.6` `G-1` 明写「离线两周攒下的量没有人测过」、队列上限未定 —— **N 是一个必须猜的数,而猜错的方向是用户看到两条一样的记录**(`U1.6` §2.3 正向要求) |
| **不设窗口** ✅ | `client_token` 唯一索引与记录同生命周期。一条记录一个 token,删记录时一并删 |

🔴 **由此得到一个必须点破的后果:删掉一条记录之后,同一个 `clientToken` 再补传会重新落一条。**

**这是对的,而且这个场景在端侧就闭合了:** 记录只有两种状态 ——
`已同步` 的记录不在离线队列里(补不了);`待上传` 的记录被删时端会同时把它移出队列(`U1.7` §2.4「离线时删除:本机即删」)。
**两条队列里都不存在「已删除但仍待补传」的条目**,所以服务端不需要为已删记录留墓碑。

**服务端不猜,也不留墓碑。** 留墓碑等于「保存一份用户要求删掉的记录的标识」,方向与 `U5.5` 相反,而它挡的是一个端侧不会发生的场景。

### 3.4 `M1-6` `POST /records/batch` 的部分成功形状

**现状已经是对的形状,本节把它补成可实现的**(`BatchCreateRecordsResponse.java:45-50`, `ItemResult` :95-104):

```
POST /api/v1/records/batch
     鉴权:登录
     body { "records": [ CreateRecordRequest, … ] }      // @Size(max = 50)
→ 200 {
    "submitted": 50, "stored": 47, "duplicated": 2, "failed": 1,
    "results": [ { "index": 0, "clientToken": "…", "status": "STORED",    "record": {…} },
                 { "index": 7, "clientToken": "…", "status": "DUPLICATE", "record": {…} },
                 { "index": 9, "clientToken": null, "status": "FAILED",
                   "error": { "code": "MISSING_CLIENT_TOKEN", "message": "…", "traceId": "…" } } ]
  }
```

🔴 **条目级失败不是请求级失败。整批恒 `200`,哪怕 50 条全 `FAILED`。**

理由:批量补传的语义是「把这 50 条各自试一次」,不是「这 50 条要么全成要么全不成」。
返回 `4xx` 会让端把整批留在队列重试,而其中 47 条已经落库了 —— 下一次重试它们全部变 `DUPLICATE`,永远不出队。

**只有整批结构性不可接受才是请求级失败:**

| 情形 | 状态 | 码 | 端 |
|---|---|---|---|
| `records` 超过 50 条 | `400` | `VALIDATION_FAILED` | **切小再传**(`U1.6` §2.4 单批上限) |
| JSON 解不开 / 未知字段 | `400` | `MALFORMED_BODY` / `UNKNOWN_FIELD` | A 档,重试无用 |
| `records` 为空数组 | `200` | — | 四个计数全 0,`results` 空 |

⚠️ **`U1.6` §2.4 写着「坏请求整批失败重试」,而结构性 `400` 重试永远不会成功。**
两句话并存会得到一个死循环。**裁定:那句「重试」指的是 B 档(5xx / 超时);A 档的整批 `400` 端必须停止重试并上报。**
这与 §2.3 是同一张表,不是两条规则 —— 登记为 `接口契约` 的一处补充,原文见 §十二 增量 3。

**四个计数为什么留着(而 `RecordPageResponse.total` 要删):**
`results` 是**全量返回**的(上限 50 条),四个计数与它同源、可自证;而端在一次补传结束时要说一句收尾话

### 3.6 🔴 `M1-12` 补传的时间戳:`batch` 的条目必须带 `occurredAt`

**两条已冻结的口径在补传路径上撞车,而现状实现了其中一条、破了另一条。**

| 出处 | 逐字 |
|---|---|
| `记一次学习` §7.5 | 「记录时间取『落本地那一刻』,**由服务端按时钟打戳,客户端不自报时间**」 |
| `U1.7` §2.2 | 「**补传回来的记录按原始落本地时间排,不用补传时刻**」 |

**在线路径上两句不冲突** —— 「落本地那一刻」与「服务端收到那一刻」相差毫秒级。
**补传路径上它们相差可以是两周**(`U1.6` `G-1`:离线时长没有上限),而服务端打戳会让第二句当场失效。

**现状已经踩上了,而且代码注释把它当成前提写了下来:**

> `RecordCursor.java` 类注释:「离线队列补传(`POST /api/records/batch`)一次落 50 条,它们的时间戳全部来自**同一次 `clock.instant()`** —— 服务端收到的时刻。」

**后果不是「排序不稳」,是「用户上周记的东西出现在今天的分组里」** ——
`U1.7` §2.2 的分组键是设备本地自然日,补传的 50 条全部落进补传那一天的分组。
而 `U1.7` 逐字写过为什么这件事贵:「用户会用『昨天第三条』来定位一条记录。顺序一变,他的结论是**『数据变了』**,而不是『排序规则变了』。」

**裁定:两个端点分开定。**

| 端点 | `occurredAt` | 理由 |
|---|---|---|
| `POST /records` | **不带**,服务端 `clock.instant()` 打戳(现状不变) | 相差毫秒级,服务端打戳既准确又不可伪造 |
| `POST /records/batch` 的每个条目 | 🔴 **必带**,`Instant`,端记录的落本地时刻 | 这是 `U1.7` 排序口径唯一的信息来源,服务端造不出来 |

🔴 **这不违反「客户端不自报时间」。** 那条规则挡的是**补记**(`U1.7` §五:「界面上没有时间选择器」),
而 `batch` 的 `occurredAt` **不是用户选的,是端在落本地那一刻记下的** —— 用户没有任何入口能改它。

**防伪造靠钳制,不靠信任(`U1.1` `A-12` 设备时钟被改的落点):**

| 情形 | 处置 |
|---|---|
| `occurredAt > now` | **钳到 `now`**,记 WARN + `clientToken`。未来时间在时间线上没有意义 |
| `occurredAt < now - N` | 🚧 **暂不设下界。** `N` 只能由 `G-1` 队列上限推出来,而 `G-1` 未定 —— **不在这里替它拍一个数**(`U1.6` §2.6 逐字) |
| 条目缺 `occurredAt` | `VALIDATION_FAILED`(条目级) |

⚠️ **`G-2`「跨零点补传的记录归到哪一天」仍然由人拍板,本节不裁它。**
本节裁的是**服务端拿不拿得到那个时刻**;拿到之后归哪一天是产品口径,而 `U1.6` §五 已点破它牵动关卡验收的输入。
**没有这个字段,`G-2` 连讨论的前提都不存在** —— 那才是本节必须现在裁的理由。

### 6.3 🔴 顺序:先鉴权,后租户列 —— 而这条顺序要落成可跑的东西

`B0` §5.4 点名了顺序,理由是「先加租户列后加鉴权,会造出『看起来分了用户其实没分』的假象」。

**把它落成一条判据,而不是一句要记住的话:**

`store.findAll(userId)` 的那个 `userId` 只能从 `CurrentSession` 来。
先加租户列就必须先造一个假的 `userId` —— 一个 `0L`、一个配置值、或者一个「默认用户」。
**而 `B0` §3.3 已经把 `0` 定成结构上不合法的 userId,起号从 `10001` 开始,正是为了让这种哨兵一眼就是错的。**

```bash
# ① 四个采集端点每一个都拿得到「进来的是谁」
grep -c 'CurrentSession' \
     server/kaodian-app/src/main/java/com/kaodian/server/api/record/RecordController.java   # 期望 4(今天是 0)

# ② 没有人拿哨兵凑数 —— 这条 grep 抓的正是「先租户列后鉴权」那条错路留下的痕迹
grep -rn '\b0L\b\|DEFAULT_USER\|defaultUserId\|SYSTEM_USER' \
     server/kaodian-app/src/main/java/com/kaodian/server/api/record/                        # 期望 0

# ③ 采集面 store 接口没有一个不带 userId 的读写方法
grep -nE '^\s+(List<Touch>|Touch|int) [a-z]' \
     server/kaodian-domain/src/main/java/com/kaodian/server/collect/TouchStore.java \
  | grep -v 'long userId' | grep -v 'append('                                               # 期望 0
```

### 6.4 存量数据

**照 `B0` §4.4 执行,不另定:** 三个文件全空 → 放行;有无 `userId` 的条目且 `kaodian.collect.accept-orphan-loss=false`(默认)→ **拒绝启动**,消息里写明三个文件各有多少条;配置为 `true` → 放行、**丢弃**、记 ERROR + 确切条数。

⚠️ **M1 这一侧多一条:`seed/touches-demo.json` 播种数据(`FileTouchStore.java:62,289`)也没有 `userId`。**
它会在**每一台全新开发机**上触发上面那条启动期拒绝 —— 而 §4.4 的第一格「三个文件全空 → 放行」在这里不成立,因为播种恰恰让它非空。

## 七、`M1-11` 删记录,与 `M5` 注销的交界

### 7.1 硬删,不软删

**三条理由,按分量排:**

1. 🔴 **覆盖度是这个产品唯一的那个指标。** 软删要给每一条查询加一个「未删除」过滤,漏一处就是「删了还算碰过」——
   而那不是一个显示 bug,是**指标失真**。硬删让这件事在结构上不可能
2. 软删是「留一份用户要求删掉的数据」,方向与 `U5.5`「注销把数据带走」相反
3. **现状就是硬删**(`FileTouchStore.delete` :172 全量重写),本条是把现状写成约定,不是改动

🔴 **`U1.7` §三 已经逐字要求过这一条,本文只是执行它:**

> 撤销 | 🚧 形态未定,当前没有撤销入口 | 🚧 未定(`G-5`)。**不要默认实现成软删除** —— 那等于替产品做了这个裁定
>
> 🔴 **最后一行是本表里唯一一条「请不要顺手做掉」的要求。** 软删除是最省事的实现,而它一旦落地,「记录能撤销、原图不能撤销」这个语义分裂就是**既成事实**,再讨论就变成改实现而不是做决定。

⚠️ **`U1.7` §五 另有一个未决口:「记录与原图能不能有不同的删除语义」,并写明「记录侧目前没有『真删就是真删』的红线承诺,所以软删在这一侧是可讨论的」。**
**本文不关这个口,而且上面的裁定不会把它关掉。** 这里裁的是**技术形态**(硬删),`U1.7` 问的是**产品可逆性**(要不要给撤销)。
两者可以并存:给五秒撤销是**端上延迟发起 `DELETE`**,不需要服务端软删 —— 也就是说,**选硬删并没有替产品把撤销那个决定做掉,而选软删会。** 要不要给撤销由人拍板,见 §十三。

### 7.2 删了不算碰过

| 被删的 | 去向 | 现状 |
|---|---|---|
| 记录本身 | **真删** | ✅ `store.delete(id)` |
| 标签 | **级联删** | ✅ `tagStore.deleteByRecord(id)`(`RecordController.java:276`) |
| 覆盖度 | **当场重算**,响应里带回新的 `node` 与 `summary` | ✅ `RecordDeletedResponse` |
| 🔴 原图 | **不删。** 走自己的生命周期,只在原图管理屏由用户手动删 | ✅ 后端本来就没有原图,这条在后端是空操作 |
| 当日计数 | **不减。** `record_created` 是「发生过」的累计(`U1.7` §2.4) | 归埋点侧,不在本模块 |

**重复删除幂等:** `DELETE /records/{id}` 删一条不存在的 → `404 RECORD_NOT_FOUND`。
⚠️ `U1.7` §三 写「重复删除应幂等」,而 `404` 不是幂等的那种形状。
**裁定:`404` 保留。** 理由:端删的是自己刚看到的一条,`404` 只可能来自「另一台设备已经删过」——
那对端是有信息的(该刷新列表),而 `204` 会把它藏起来。**端把 `404` 当成删除成功处理**,这条写进契约,不是让服务端改状态码。

```bash
# 判据 ①:删除带 userId —— 「知道 id 就能删别人的记录」这条路不存在
grep -n 'delete(' server/kaodian-domain/src/main/java/com/kaodian/server/collect/TouchStore.java   # 期望签名含 long userId

# 判据 ②:软删的痕迹一处都没有
grep -rniE '\bdeleted\b|\bsoftDelete|deletedAt|is_deleted|回收站' \
     server/kaodian-domain/src/main/java/com/kaodian/server/collect/                                # 期望 0
```

### 7.3 🔴 与 `M5` 的唯一交界面:一个方法,不是一个循环

**`M5` 注销要删一个用户的全部记录。最省事的实现是循环调 `delete(userId, id)`。**

**那条路必须在这里堵掉,因为它的代价是不可见的:** `FileTouchStore.delete` 每次**全量重写整个文件**并 `fsync`(:410-443)。
一个记了三年的用户注销一次 = N 次全量重写。文件态下是几分钟,MySQL 态下是 N 次单行删除加 N 次索引维护 ——
**而注销是一个用户按下之后必须完成的动作,超时了没有第二次机会。**

| 交界面 | 归谁 |
|---|---|
| `TouchStore.deleteAllOf(long userId)` / `RecordTagStore.deleteAllOf(long userId)` —— **签名与语义** | **M1 定义**(它是 `collect` 包的事) |
| 什么时候调、调完之后账号怎么办、导出在删之前还是之后 | **M5 编排**,M1 不写 |

🔴 **除这两个方法之外,`M5` 不碰 `collect` 包一个符号。**
这条有编译期保证:`kaodian-auth/pom.xml` 不依赖 `kaodian-domain`(实测 :23-27 只有两个 starter),
所以注销的编排只能落在 `app` —— **依赖图本身就是这条边界的执行装置。**

```bash
# 判据:auth 够不到 collect
grep -n 'kaodian-domain' server/kaodian-auth/pom.xml                                    # 期望 0 命中
grep -rn 'TouchStore\|RecordTagStore' server/kaodian-auth/src/main/java                 # 期望 0 命中
```

### 增量 2 · §1.5 幂等,业务键那一行补两句

> **唯一性是 `(userId, clientToken)` 组合唯一,不是 `client_token` 全局唯一。** 全局唯一的后果是 A 的补传被 B 的记录去重掉 —— 静默丢一条,而接口返回 `200`。
>
> **不设去重窗口。** `client_token` 与记录同生命周期,删记录时一并消失。设 N 天窗口的后果是离线超过 N 天的一批记录补传时产生第二条,而 `U1.6` `G-1` 明写离线时长上限未定、没有实测过 —— **N 是一个必须猜的数,猜错的方向是用户看到两条一样的记录。**

### 增量 3 · §1.3 错误体之后,补一张「端要不要用户动手」的表

> **端要的二分不是 4xx/5xx。** `U1.6` §三 要求「4xx 与 5xx 必须可区分」,理由是「一个要用户动手,一个用户什么都不用做」;而 `401 TOKEN_EXPIRED` 是 4xx,要的却是「用户什么都不用做」(`U1.1` `A-09`:续期是静默的)。**契约给的是下面这张表,不是 HTTP 类别:**
>
> | 响应 | 端的动作 |
> |---|---|
> | `2xx` | 出队 |
> | `401` / `403` | **留队**;`TOKEN_EXPIRED` 续期后自动重发,其余引导登录、登录后自动继续 |
> | 其余 `4xx` | 该条标失败并**保留在本机**,给「删掉它 / 改一下再传」两条路 |
> | `5xx` / 超时 / 断连 | 留队,自动重试 |
>
> **连带:`POST /records/batch` 的条目级失败不是请求级失败,整批恒 `200`。** 返回 `4xx` 会让端把整批留在队列重试,而其中已落库的那些下一次全变 `DUPLICATE`,永远不出队。只有整批结构性不可接受(超 50 条 / JSON 解不开 / 未知字段)才 `400`,**而 A 档 `400` 端必须停止重试并上报** —— `U1.6` §2.4「坏请求整批失败重试」那句指的是 5xx,直接执行会得到死循环。

### 增量 4 · §1.4 分页,`limit` 那一行补一处落差登记

> ⚠️ **2026-09-03 实测落差:`RecordController.java:306-308` 的 `limit` 是 `1..200` 默认 `50`,超界回 `VALIDATION_FAILED`;本节定的是 `1..100` 默认 `20`,超界回 `400 INVALID_LIMIT`。** 三处都不一致。裁定:本节赢,归 `M1` 执行。实测 `web/src/api/queries.ts:28` 只拉第一页且不传 `limit`,改动对前端零影响。

### 增量 5 · ⚠️ 这两段进 `后端系统设计与组件接入`,不进 `接口契约`

> **§1.2 那张时序图之后,加一条指针(🔴 不改图):** ⚠️ 图上 `S--)T: 提交打标任务(带字节,内存传递)` 画的是一次往返,而实际是两次:`POST /records` 的请求体六个字段里没有 `byte[]`(`CreateRecordRequest.java:67-90`),字节走第二次往返 `POST /records/{id}/image` 或 `/audio`。**这不是图画错了,是图画的是「记录先落地、识别在后」这个意图** —— `U1.1` 推论 2 逐字要求「识别是第二次往返,不是第一次的后半段」,而两次往返正是那条推论的落地形态。落法见 `M1-记录采集与离线补传` §5.1。
>
> **§五 音频那一段,补一处落点更正:** ⚠️ 本文写「≤60s 上限在 `CaptureService` 里校验」,实测在 `RecognitionController.java:401`,且 `CaptureService` 的构造器四个参数里没有 `AsrClient`。**裁定保留现状**:校验的是 HTTP 请求的可接受性(`413`/`415`),天然是 web 层的事;「上限会随供应商变」这个理由要求的是「上限是配置值不是字面量」,而不是「上限住在 domain 里」。落法见 `M1-记录采集与离线补传` §4.1。

### 增量 7 · §1.1「时间」那一行之后,补补传路径的例外

> **`POST /records/batch` 的每个条目必带 `occurredAt`,`POST /records` 不带。**
>
> `记一次学习` §7.5「客户端不自报时间」与 `U1.7` §2.2「补传回来的记录按原始落本地时间排」在补传路径上撞车:在线时两个时刻相差毫秒级,补传时相差可以是两周(`U1.6` `G-1` 未设离线时长上限)。服务端打戳会让一批补传记录**全部落进补传那一天的分组**,而 `U1.7` 逐字写过代价:「用户会用『昨天第三条』来定位一条记录,顺序一变,他的结论是『**数据变了**』」。
>
> 🔴 **这不是「客户端自报时间」的例外,是那条规则本来就没管的场景** —— 它挡的是**补记**(`U1.7`:界面上没有时间选择器),而 `occurredAt` 是端在落本地那一刻记下的,用户没有任何入口能改它。
>
> **防伪造靠钳制:** `occurredAt > now` → 钳到 `now` 并记 WARN(`U1.1` `A-12` 设备时钟被改的落点);下界暂不设,因为它只能由 `G-1` 队列上限推出来,而 `G-1` 未定 —— **不在这里替它拍一个数**。`G-2`「跨零点补传归哪一天」仍由人拍板,但**没有这个字段,`G-2` 连讨论的前提都不存在**。

### 增量 8 · §10.4 记录与打标,`MISSING_CLIENT_TOKEN` 那一行补一句

> **HTTP 列写 `—` 不是漏填:它只在 `POST /records/batch` 的条目级 `error` 里出现,从不作为响应状态。** 条目级错误码全集是 `MISSING_CLIENT_TOKEN` / `MISSING_NODE_CODE` / `NODE_NOT_IN_SYLLABUS` / `VALIDATION_FAILED` 四个,🔴 **不含 `SERVER_ERROR`** —— 一条落库失败就是整批写入层出了问题,那是请求级的事,混进条目里会让端把它当成「这一条不可接受」而停止重试。

```bash
$ grep -rn 'hasMore\|\.total' web/src        # B0 §16.1 指定的命令,基线 81a2c23

web/src/api/derive.ts:59:  if (page.returned !== page.total) return null
```
