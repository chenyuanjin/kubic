技术选型调研 · 2026-08-30 · Windows · Linux · macOS · Web · Android · iOS · 鸿蒙 · 小程序 · H5


九个交付目标，没有任何一个框架能全覆盖。这份手册按「共享什么」而不是「用哪个框架」来组织，并明确标出哪些地方跨端会直接伤害体验——那些地方应该写原生。

**九个交付目标**：Windows · Linux · macOS · Web · Android · iOS · HarmonyOS · 小程序 · H5

## 00 · 三条结论

如果只看一屏，看这里。

### 一 · 九端没有单一答案，最少要两套栈

桌面三端 + Web 是一个技术域（WebView / 自绘 / 原生控件），移动 + 鸿蒙是第二个域，小程序是第三个**被沙箱隔离的**域。小程序不交出渲染树、不交出 JS 引擎句柄、禁止 `eval`、逻辑层没有 `document`——这四条决定了 **React Native 和 Flutter 在物理上编译不到小程序**。任何号称「一套代码九端」的方案，要么在小程序端换了另一套运行时，要么在骗你。

### 二 · 2026 年最大的选型变量是治理，不是性能

三大框架的归属在过去 18 个月同时重构了：React Native **已不归 Meta**，转入 Linux Foundation 托管的 React Foundation（八家白金创始成员含微软、亚马逊、**华为**）；Flutter Desktop 的 lead maintainer **由 Google 交给了 Canonical**；Material/Cupertino 正被拆出 Flutter SDK。做五年期押注时，这比任何 benchmark 都重要。

### 三 · 「100% 跨端」应当是反目标

这句话出自把全部 App 迁到 React Native 的 Shopify 自己。桌面小组件、Live Activity、Apple Watch、App Intents、后台长任务、持续 BLE、端上 AI 模型——这些在所有跨端方案里都必须写原生。正确的问法是 native **and** cross-platform，不是 native **or** cross-platform。

> “100% React Native should be an anti-goal.”\
> —— Shopify Engineering，2025-01，全量迁移 RN 五年复盘

## 01 · 先分清三种「跨端」

同一个词指着三件成本、风险、体验上限完全不同的事。混谈是选型翻车的头号原因。

| 路线 | 做法 | 体验上限 | 典型代表 | 风险结构 |
|----|----|----|----|----|
| 只共享逻辑 | 网络 / 数据 / 状态 / 加密跨端，UI 各写各的 | ✅ = 原生 | KMP、Rust+UniFFI、C++ | 最低。Google 官方只背书这一档 |
| 映射原生控件 | 跨端框架描述 UI，最终 mount 到系统组件 | 接近原生，**系统换皮自动跟随** | React Native、Lynx、.NET MAUI | 中。受制于两端控件差异 |
| 自绘 | 自带渲染引擎把界面画到一块画布上 | 像素级一致，但**永远在追系统设计语言** | Flutter、Compose MP、Avalonia、Qt | 中高。iOS 设计语言是结构性债 |
| WebView 容器 | 系统 WebView 跑 Web 应用 + 原生桥 | 受 WebView 能力硬顶 | Capacitor、Tauri、Electron | 低（技术）/ 高（体验天花板） |

> ⚠️
>
> #### 2026 年新出现的结构性差距
>
> 自绘路线跟不上 Apple 年度设计语言，**这一次是两家厂商在官方材料里同时承认的**。Flutter 2026 Q2 官方调查里 Cupertino widgets 满意度 61%，全项最低、跌幅最大；Google 原文承认 “Flutter's promise of native-feeling apps hadn't kept pace specifically for iOS-style design”，Liquid Glass 要等 Material/Cupertino 解耦完成后才能开始追。JetBrains 的官方文档更直接：要在 Compose Multiplatform 里用上 Liquid Glass，**“you need a native SwiftUI shell”**——Compose 侧渲染不出来。
>
> 映射原生控件的路线（RN / Lynx / MAUI）在这一点上结构性占优：它们的 `TabView`、`NavigationStack`、toolbar 本身就是系统组件。

## 02 · 桌面三端 + Web

Windows / Linux / macOS 的真实分歧点是 Linux，以及「要不要 Web」。

### Electron

（v44 · Chromium M152 / Node 24）**✅ 三端一致的默认答案**

**九端覆盖**：Win✅ · Lin✅ · mac✅ · Web◐ · And✕ · iOS✕ · 鸿蒙✕ · 小程序✕ · H5✕ —— 前端代码可复用到 Web，外壳不可

自带 Chromium，所以三端渲染**完全一致**——这是它唯一但极其值钱的卖点，也是设计工具、富文本编辑器、协作白板离不开它的原因。VS Code、Slack、Discord、Notion、Figma 桌面版、Claude 桌面版都是它。

**最被低估的长期成本**：8 周一个大版本、只跟 Chromium 双数版本、**只有最新 3 个 major 有安全支持**。等于每年必须做 6 次 Chromium 大版本升级回归，否则 8 个月内就跑在无安全补丁的 Chromium 上。团队要为此常备人力。

> ⛔ 别用于：多窗口/多实例工具（每个实例是一整套 Chromium，内存线性叠加）、低配老旧终端（工厂 / POS / 车载）、体积敏感的内网批量分发。

### Tauri

（2.11.5 · 2026-07）**⚠️ Windows/macOS 优先时才选**

**九端覆盖**：Win✅ · Lin◐ · mac✅ · Web◐ · And◐ · iOS◐ · 鸿蒙✕ · 小程序✕ · H5✕

体积和内存确实是 Electron 的零头（3–15 MB vs 80–200 MB 量级），Rust 后端的能力/权限模型（capability + permission + scope）比 Electron 的 `contextIsolation` 细得多。但代价全部集中在一个地方：**它用系统 WebView**。

#### Linux 是它的阿喀琉斯之踵

以下全部来自 Tauri 官方调试文档，不是社区传闻：NVIDIA + WebKitGTK 的 DMABUF 渲染器冲突会导致**白屏、resize 闪烁、无错误信息直接崩溃**；变通手段要逐级降级到 `WEBKIT_DISABLE_COMPOSITING_MODE=1`（等于关掉整个加速合成）。最致命的是**静默失败**——WebGL2 context 创建会成功但可能落到软件光栅化，而 WebKitGTK 出于指纹防护把 `WEBGL_debug_renderer_info` 一律伪装成 `Apple GPU`，**你在前端根本无法探测自己是不是在软件渲染**。用户报「卡」，你在支持工单里无法诊断。

macOS 侧的隐性约束：WKWebView 跟随 OS 更新，**你的 CSS/JS 特性下限 = 你支持的最老 macOS**。

> ⛔ 别用于：Linux 是主要平台且 UI 有 WebGL/Canvas 重负载（终端、编辑器、地图、实时图表）；需要三端像素级一致的产品；必须支持较老 macOS；团队不愿投入 Rust。

### Flutter Desktop

（3.47 · 2026-08-12）**⚠️ 移动端的延伸，不是桌面首选**

**九端覆盖**：Win✅ · Lin✅ · mac✅ · Web◐ · And✅ · iOS✅ · 鸿蒙◐ · 小程序✕ · H5✕

3.47 起 **Impeller 在桌面三端成为默认渲染器**（macOS Metal，Win/Linux Vulkan），Skia 的 opt-out 开关官方明说「未来版本移除」；桌面新增 SDF 文本渲染，针对低 PPI 屏优化清晰度。

#### 治理层面必须知道的一条

Google 在 I/O 2026 确认 **Canonical 成为 Flutter Desktop 的 lead maintainer 与 strategic steward**。正面看是有了专职团队（Ubuntu App Center / Firmware Updater / Security Center 都是 Flutter 写的）；负面看是**桌面端路线图不再由 Google 决定**。Windows-first 的商业桌面软件需要评估这一点。

> ⛔ 别用于：有强制无障碍合规要求（桌面走 MSAA，是明确短板）；需要成熟多窗口/停靠面板（API 仍 experimental）；CJK 输入法是核心交互（3.47 还在修 Windows 韩文光标定位这种基础问题）；**纯桌面、无移动端计划的项目**。

### Avalonia · Uno · .NET MAUI

（Avalonia 12 / Uno 6.6 / MAUI 10）**◐ 只在已有 .NET 团队时考虑**

**Avalonia 12**（2026-04）是 .NET 跨平台 UI 的事实标准，全自绘 SkiaSharp。它做了一件别人没做的事：**Linux 原生无障碍（AT-SPI2）后端，.NET 生态首个**。对政企 / 医疗 / 教育的 Linux 采购这是硬指标，目前没有别的 .NET 框架能满足。12.0 还默认开启 compiled bindings、WebView 组件从商业版开源。Wayland 仍在私测。

**Uno 6.6** 的路线是「写 WinUI 跑遍所有平台」，对存量 UWP/WinUI/WPF 资产是最短迁移路径，且 **WASM 是一等公民**。6.6 补上了两块关键短板：Skia 自绘下的读屏（Windows/macOS/WASM 已可用，**Linux 仅在计划中**）和**全端完整 IME composition**——这是自绘阵营在中日韩输入上的关键补完。五端 Native AOT 冷启动实测：Windows 1.605s → 0.824s，Linux 0.870s → 0.350s。

**.NET MAUI** 要说实话：采用率有限，社区一致观察是开发者受困于 bug 与更新缓慢，微软自己也几乎不用它；Linux 桌面官方立场是 **not planned**；**无 LTS 版本**。反而是 Avalonia 在 2026 年 3 月给 MAUI 做了个后端来补 Linux 和 WASM，微软未背书。

> ⛔ 新启动的跨平台桌面项目不要选 .NET MAUI。.NET 团队做桌面优先选 Avalonia；有 WinUI 存量且 Web 是一等目标选 Uno。

### Qt

（6.11 / 6.12 (2026-09)）**◐ 工业、医疗、汽车的既定答案**

生产验证时长最长、领域最重的一个：Maya、DaVinci Resolve、Telegram Desktop、KDE、大量汽车 IVI 与工业 HMI。RHI 抽象层给到 D3D/Metal/Vulkan/OpenGL 的完整控制，6.11 甚至给 QML 加了用户自定义 render pass 的 API——跨平台框架里独一份的底层控制力。

**授权是第一道闸门，两个陷阱**：部分模块**只提供 GPL**，用了就要 GPL 整个应用；**同一应用内不允许混用开源与商业许可**。LGPLv3 要求动态链接且允许用户替换 Qt 库——嵌入式场景常常做不到。

> ⛔ 别用于：前端技术栈团队（招聘池完全不同）；需要快速迭代的消费级应用；只是想要一个漂亮的现代 UI（你在为用不到的 90% 付钱）。

### Web 复用：谁能真的一套代码同时出桌面和 Web

| 等级 | 框架 | 真实成本 |
|----|----|----|
| ✅ 天然复用 | Tauri / Wails / Electron 渲染层 / Dioxus | 前端本来就是 Web。成本在**能力抽象层**：文件系统、托盘、原生菜单在 Web 端不存在，必须设计 capability 抽象与降级 |
| ◐ 能出但有约束 | Flutter Web / Compose Wasm / Avalonia WASM / Uno WASM / Qt WASM | 都是「把应用画到 canvas」，见下方共同硬伤 |
| ✕ 不行 | .NET MAUI（除非套 Avalonia 后端） | — |

> ⚠️
>
> #### Flutter Web 的 Wasm 路径被严重误传
>
> 官方文档自己写明：**Firefox 120+ 虽支持 WasmGC 但有已知 bug 阻塞 Flutter Wasm 渲染器**（bugzilla #1788206）；**Safari 同样有阻塞 bug**（webkit #267291）；**iOS 上任何浏览器都跑不了 Flutter Wasm**（强制 WebKit）。结论是 2026 年 8 月 Flutter 的 Wasm 渲染路径**实际只在 Chromium 系桌面浏览器生效**，其余一律回退 JS + CanvasKit（+1.5 MB）。Flutter 官方自己也承认博客这类文本密集内容更适合 DOM 模型，并推荐用 Jaspr——flutter.dev 官网自己就是 Jaspr 建的。

**所有 canvas 类 Web 方案的共同硬伤**：SEO 为零；无障碍是硬仗；首屏体积远大于同等 Web 应用；浏览器原生交互（Ctrl+F 查找、翻译、密码管理器自动填充、文本选择、阅读模式）统统要框架自己重新实现，且往往不完整。**Uno 是少数明确解决了 WASM 读屏的**。

## 03 · Android / iOS

这是生态最成熟、也是「共享层怎么切」最值得推敲的一域。

### Flutter

（3.47 / Dart 3.13 · 2026-08-12）**✅ 自绘阵营的成熟选择**

渲染

Impeller：iOS **唯一**（无法切回 Skia）；Android API 29+ 默认，低版本回落 OpenGL；桌面 3.47 起默认；Web 仍 Skia

官方满意度

总体 93% top-2；信任 Flutter 83%，**信任 Google 仅 62%**

最弱项

Cupertino widgets **61%**，全项最低且跌幅最大

体积数据

**官方停在 2021-03**，无 2024–26 任何官方数字

**2026 下半年启动项目必须排期的破坏性变更**：Material/Cupertino 拆出 SDK（核心 SDK 内旧库 **11 月正式弃用**，全生态迁移）；iOS 最低版本 13→15、macOS 10.15→12；**iOS 27 SDK 强制 UIScene 生命周期**，自定义 `AppDelegate` 或 legacy lifecycle 插件必须手工迁移，否则启动即失败；SwiftPM 自 3.44 起为默认，CocoaPods 进入维护模式；Intel Mac 已停自动化测试。

**好消息**：原生互操作 2026 年确实变好了。3.38 起 `--template=package_ffi` + build hooks 让原生构建**不再需要任何 OS 特定构建文件**（无 CMakeLists / podspec / build.gradle）。但 Swift 仍需 `@objc` + ObjC 头绕一圈，且 **Dart isolate 不绑定线程**（VM 可能无预警换线程）是真实的坑。

> ⛔ 别用于：必须第一时间跟进 Apple 年度设计语言的品牌型消费 App；Widget / Live Activity / watchOS 独立 UI；需要 3D（官方 FAQ 明说不支持 OpenGL ES）；需要 ABI 兼容性（官方明说 not a current goal）。

### React Native + Expo

（0.87 / Expo SDK 57 · 2026-08）**✅ 招聘与生态最优**

**New Architecture 已经不是「默认」而是「唯一」**——这是需要纠正的关键点。0.76 是 by default，**0.82 是第一个完全跑在 New Architecture 上的版本**，0.84 起 iOS 构建默认不含 legacy 代码，0.87 移除 `useTurboModules` flag。仍在讨论「要不要迁 New Arch」的项目，实际讨论的是「要不要升级 RN」。

**Expo 已是文档层面的事实标准**：RN 官方 Get Started 页原文推荐 Expo，新项目唯一文档化路径是 `npx create-expo-app@latest`；自 0.80 起每篇 release blog 都有 Expo 工程师联合署名。

#### 2026 年真实发生的生产回归

Hermes V1 自 0.84 起为默认引擎，但在 Expo SDK 56/57 引入两个回归：导入 `react-native-worklets` 或 `reanimated` 的 App 内存占用 “drastically increase”（expo#46519）；开发期启动变慢（expo#48298）。**动画/手势库是 RN 生态最核心的依赖，这类回归爆炸半径很大。**都在 8 月修复。

**React Server Components 不是生产选项**：Expo 官方自己写 “Production deployment is limited and not recommended yet”，且 EAS Update（OTA）不支持 RSC、`StyleSheet.create` 与 `Platform.OS` 在原生端不可用、Hermes 上嵌套 Server Function 不支持、full RSC 模式下 `Stack`/`Tabs`/`Drawer` 全部不支持。

唯一可信的生产性能数据来自 Shopify（全量 RN）：**screen load \< 500 ms (P75)、crash-free session \> 99.9%**。

> ⛔ 别用于：供应链攻击面必须最小的场景（金融/加密/政企——Shopify 自己把这列为主要负面经验）；团队里没有任何原生工程师（Shopify 原文：“Native devs are crucial”）；后台长任务 / 持续 BLE / 端上 AI / Apple Watch / App Intents；无法承受每年 6 次版本升级节奏。

### Kotlin Multiplatform（只共享逻辑）

（Kotlin 2.4.10）**✅ 风险最低的一档，已被巨头验证**

Google 的官方措辞值得逐字读：**“officially supported by Google for sharing business logic between Android and iOS”**，而 CMP 被表述为 JetBrains 的东西、“can also”。这个定位从 2024 年 I/O 至今没变。

工程承诺是实的：Jetpack 的 KMP 支持中 **iOS 与 Android/JVM 同列 Tier 1**（CI 全量设备端测试、跟踪源码与二进制兼容性）；Android 团队自建了 iOS 支持的 annotation / collection / datastore / lifecycle / viewModel / paging / **room** / savedstate / sqlite；Room 3.0 是围绕 KMP 重构的大版本。

生产名单：Google Workspace、Booking.com、Duolingo、Forbes、X、McDonald's、百度 Wonder、Philo。

#### 生态缺口（最容易忽略）

- **Firebase 无官方 KMP SDK**，只能用社区 GitLive
- **Dagger 完全无 KMP**；DataStore 只有 Preferences 没有 Proto
- Room KMP **无预打包数据库**，非 Android 平台 DAO 必须是 `suspend`
- Apple 目标的最终二进制**只能在 macOS 主机构建**——CI 无 macOS runner 是结构性成本，无解
- Xcode 里**没有 Kotlin 语言支持**，调试靠非官方 LLDB 插件（JetBrains 已把这列为 2026-08 路线图重点，等于官方承认）

### Compose Multiplatform（连 UI 一起共享）

（1.12.0 · 2026-08-25）**⚠️ 中文 App 要专门验证输入法**

**「CMP iOS 已 Stable」是半个事实**：核心 Runtime/UI/Foundation 是 1.12.0 stable，但 **Material3 是 1.12.0-alpha03、Navigation 是 2.10.0-alpha02**。设计系统与官方导航库在 CMP 侧仍是 alpha，社区导航库同样滞后。**导航是 CMP 生态最不成熟的一块。**

#### 对中文 App 最关键的几条（YouTrack 可核实，全部 Open）

- **CMP-2092**：中文输入时无法直接删除最后一个字符（长期 Open）
- **CMP-10706**：CJK 文字选择行为与 iOS 原生不一致（Major）
- **CMP-10600**：交互式收起键盘（向下拖列表关键盘）**完全不支持**（Major）
- **CMP-3141**：无 warm-up API，自 2023-05 Open 至今——这直接否定了「在大型原生 App 里插一两个 Compose 页面」这个用法
- **CMP-10695**（2026-08-25 新报，Major）：`SecureTextField` 把密码明文暴露给 VoiceOver

原生文本输入（NITI）1.11 引入，到 1.12 **仍是实验性 opt-in**，官方原话是「现有的 Compose 文本输入仍是 stable choice」，默认化无排期。

#### 但它有一个别人没有的风险结构优势

**CMP 的降级路径是渐进的。**`expect/actual` 允许把任意一屏换成原生 SwiftUI/UIKit view，同时保留同一份 KMP 数据层。**选错不等于重写，只需按需替换 iOS UI 层**——这是相对 Flutter/RN 的核心差异。Sony（Sound Connect）迁移时就准备了退回 SwiftUI 的方案，只是没用上。

> ⛔ 技术上不可能：Widget / Live Activity / App Clip / watchOS UI（YouTrack 里连 feature request 都没有）。别用于：中文输入是核心交互（IM、笔记）；无障碍是硬合规；iOS 主导而 Android 是附属端的团队——共享 UI 的收益模型建立在「Android 侧已经是 Jetpack Compose」之上，反向不成立。

### Capacitor / Ionic

（8.5）**◐ 工具型 App 的最优解**

被低估也被高估。**够用且是最优解的场景**：企业内部工具 / B2B 后台移动端、内容型 App、表单密集型（保险、医疗问卷、现场巡检、工单）、已有 Web 应用要上架、需高频热更新的运营型产品。

**结构性天花板（不是调优能解决的）**：iOS 上 rAF / canvas / WebGL **硬顶 60 fps**（WebKit bug 294338，一年多无人认领）；全异步 JSON 桥，**无同步原生调用**，大 blob 绝不能走桥；JS bundle 500 KB–5 MB，低端机 5 MB 约等于 5 秒启动。

> ⛔ 别用于：手写笔 / 绘图 / 白板；游戏与实时 canvas/WebGL；JS 驱动的物理动画与手势跟手交互；万级 item 的复杂列表（DOM 虚拟化打不过 RecyclerView / UICollectionView）；AR / 实时音视频处理 / 连续 BLE。

### Lynx（字节）

（4.0）**⛔ 只适合当动态化容器**

需要纠正一个常见误传：**Lynx 移动端是映射原生控件，不是自绘**（只有桌面端 Clay 是自绘）。双线程架构 + IFR 让首屏有真实的架构优势。

但：插件 Autolink 到 3.9 才有、生态几乎为零、`@lynx-js/react` 仍是 0.x、lynx-ui 是 headless、**字节以外无任何可核实的生产案例**、单一厂商无公开支持策略。

> ⛔ 唯一被验证的形态是**已有原生 App 内的动态化容器**（TikTok 的用法）：活动页、电商店铺页、搜索面板，要求首屏极快、发版频繁、UI 高度定制。如果你的问题恰好是这个，值得做 POC。做主干不要碰。

## 04 · 鸿蒙

这是九端里唯一「跨端方案能不能少写点」需要单独回答的一端。

先给出直接答案，分三种问法：

| 你的问题 | 答案 |
|----|----|
| 一套代码从零覆盖三端、做重交互 App 主干 | ✕ **不存在。**ArkUI-X 不成熟且方向是反的；uni-app x 最接近，但官方文档自己写着「降低期望、别用双端标准验收」 |
| 已有 Flutter / RN / Taro / H5 存量，能不能少写点 | ✅ **能，这是当前最靠谱的路径。**别指望零成本，指望 30%–70% 复用率 |
| 工具类 / 企业应用 / 信息展示类 | ✅ **Capacitor / Cordova 完全够用。**前端团队直接开工 |

### 四条路线的成熟度

| 方案 | 维护方 | 评级 | 关键事实 |
|----|----|----|----|
| ArkTS + ArkUI 原生 | 华为 | ✅ A | 唯一满配路径。一多、实况窗、卡片、意图框架、分布式流转只有原生能拿到 |
| RNOH | **华为 + Software Mansion** | ◐ B | 不是野生项目。Software Mansion 是 Reanimated / Gesture Handler 的作者，从零实现了 OpenHarmony 版 TurboModule。走 ArkUI **C-API** 而非 ArkTS。生产案例：小红书、携程、YY。计划适配 368 个三方库，已适配 205 个 |
| Flutter-OH | OpenHarmony 社区 SIG | ◐ B | 2026 年跟版滞后从 7 个月压到 **4 个月**；规划 200+ 高优先级三方库鸿蒙化。**官方自认**内存占用偏高、负载高于其他框架 |
| ArkUI-X | 华为 | ✕ C | **主线自 2026-01 起 7 个多月无新 Release**；且它解决的是「已有鸿蒙原生想复用到 Android/iOS」，**方向与多数团队需求相反**；无可信商业生产案例 |

> ⛔
>
> #### 大厂的做法收敛到了同一个答案
>
> **没有一家旗舰 App 是纯跨端做的。**微信是完全原生重写（295 天）；企业微信一年百万行代码；小红书是 **ArkTS 原生底座 + 自研一多框架 + RNOH + 自研播放器**的混合架构，约 200 万行代码；京东用 Taro 编译到鸿蒙原生并把运行时下沉 C++（首页 1062 ms，比纯 ArkTS 版快 23.9%；商详 560 ms，快 74.2%）；美团是 Rust 底层逻辑 + RN 容器 + ArkUI 原生 UI。
>
> 正确姿势不是「选一个跨端框架代替重写」，而是 **UI 主干认命做原生，逻辑层（C++ / Rust / KMP / JS）尽可能复用，动态化业务用跨端容器承载**。

### 两个必须知道的工程坑

- **ArkTS 的 GC 与 V8 不同，很容易内存泄漏。**小红书和 uni-app x 官方文档独立提到同一件事。必须在项目早期就把 DevEco 内存分析工具接进流程。
- **Worker 不能跨 HAP/HSP 调用**；Sendable 有传染性；TaskPool 任务超 3 分钟被系统自动回收；`LazyForEach` 忘指定 key、空 callback 堆积、大对象 `JSON.stringify`、Image `syncLoad` 网络资源都是实测出的性能热点。Code Linter **不能挂 Git pre-hook**，本地提交仍需手动跑脚本。

## 05 · 小程序 + H5

被沙箱物理隔离的一域。这里的约束是「不能」，不是「不好」。

> ⛔
>
> #### 为什么 RN / Flutter 到不了小程序
>
> 小程序是**不交出渲染树、不交出 JS 引擎句柄、不执行原生二进制、禁止动态执行代码**的沙箱。四条禁令都有官方原文：`eval` / `new Function` 禁令；逻辑层无 `window`/`document`（**无法同步测量**）；视图层不跑开发者 JS；`WXWebAssembly.instantiate` 的 path 必须是代码包内路径，不能从 ArrayBuffer 实例化。
>
> RN 的 Fabric 靠 **JSI 拿 C++ Runtime 指针**，Mount 落到平台原生 View，Yoga 需要宿主**同步**测文本——四条小程序全无。Flutter 侧：CanvasKit +1.5 MB / skwasm +1.1 MB，**光引擎就吃掉微信 2 MB 主包的四分之三**。

### 两条 2026 年的重要变化

### uni-app x 战略掉头：蒸汽模式

**⚠️ 性能亮眼，生产验证水位是问号**

DCloud **放弃了「UTS 编译成 Kotlin/Swift/ArkTS」作为主线**，改成 JS/TS 驱动 + 自研原生 UI 框架：`template`/`style` 直接编译为 C 代码，走原生渲染管线但几乎不用系统组件。官方解释是蒸汽引擎把跨语言通信折损压到 5% 以内，而渲染快出 2–3 倍，于是换回 JS 以换取动态性、生态和 AI 友好度。

官方 benchmark（DCloud 自测，但**原生对照源码全部开源可复现**）：4050 个 view+text 创建，Android Fold4 上原生 View 461.8 ms / Compose 625.8 ms vs 蒸汽 229.2 ms；死亡长列表平均帧率 Android 原生 View 45.35 vs 蒸汽 109。

**代价清单**：仅组合式 API、不支持 mixin；CSS 运行时**不支持关系选择器**（必须 BEM）；样式隔离策略 2.0 要求三方组件适配；`list-view` 复用规则严苛；**打包后目前不能热更新**。

**最大的问号**：DCloud 官方原文——「由于 uni-app x 没有运行时数据采集，所以 DCloud 并不知道哪些开发者在真实使用 uni-app x」。公开案例约 100 条，全是工具 / OA / 教育 / 政务 / 物联网中小 App，**明确标注蒸汽模式的只有 2 个**。对比 Taro 拿京东 App 核心购物链路做背书，验证强度不在一个量级。

### Taro 4.2.1

**⚠️ React 栈唯一选择，但 RN 端已冻结**

需要纠正两点：**不存在 Taro 5.x**；**Taro 4.x 并没有推翻 Taro 3 的重运行时架构**，小程序端仍是「逻辑层模拟 DOM/BOM → 虚拟 DOM 序列化 → setData」。4.x 的全部架构投入都在鸿蒙 C-API 上——想要小程序端性能，Taro 4 相对 Taro 3 没有质变。

**RN 端按不可用处理**：`rn-runner@4.2.1` peerDeps 钉死 `react-native ^0.73.1 / expo ~50`（社区已 0.87）；RN 0.76 适配 2024-11 就在 canary 至今没进 beta；**官方模板第一条命令就跑不通**（issue #19486，0 回复）。

React 版本停在 **^18**（无 19）。Vite 模式是鸿蒙的入场券但不是小程序端推荐项——采用率约 20%，且 Taro 的 Vite 锁在 `vite ^4 + rollup 3`（2023 年工具链）。

| 项目 | 判定 | 最后动作 |
|----|----|----|
| Mpx（滴滴） | ✅ 活跃 | 2026-08-28 push / 2.11.1。编译期增强 + MobX 依赖收集，按路径增量 setData。**但核心维护高度集中于一人** |

### 微信 Skyline 与一个最容易踩的坑

引擎 1.4.22（2026-08-26），月度更新，已 GA。架构不是移除双线程，而是「AppService 线程建树 ↔ 渲染线程无 JS」，收益是消掉 JSBridge 序列化、内置组件下沉原生、**`setData` 不再有通信和序列化开销**。官方数据首屏 −66%、内存单页 −35%。

> ⚠️
>
> 官方加粗原文：**「由于 Skyline 默认接入 We 分析的 AB 实验，未配置的情况下，页面渲染仍为 WebView 引擎」**，且「AB 实验流量 100% 并不代表全量，而是 Skyline 和 WebView **各 50%**」。需要显式 `disableABTest: true`。很多团队以为自己在用 Skyline，其实一半流量没有。

**兼容性代价很重**：无 inline 布局、无 BFC、`overflow:scroll` 不支持、无 sticky、无属性选择器、z-index 仅兄弟、`web-view`/`movable-view`/`editor` 不支持、只能自定义导航、动画手势必须 worklet。

### H5 的能力边界

> ⛔
>
> #### 对选型影响最大的一条
>
> **iOS 的 WKWebView 里 Service Worker 完全不可用**，连带 Web Push 也不可用，存储配额只有磁盘 ~15%（浏览器 / 主屏 web app 是 ~60%）。**「H5 在浏览器里」和「H5 在你自己 App 的 WebView 里」在 iOS 上是能力完全不同的两个东西。**

- **Web Bluetooth / NFC / USB / Serial / HID**：WebKit 书面列入「**决定不实现**」清单——不是「暂时没有」
- **后台同步 / 周期同步 / Background Fetch / 后台定位**：iOS 全部为零
- ITP 7 天清除仍在（清 IndexedDB / localStorage / SW cache），但**主屏幕 web app 豁免**——这是 iOS 上做离线 H5 的唯一可靠路径
- 能用的：WebGPU（iOS Safari 26 起默认）、WebGL2 / Wasm threads / SIMD、Wasm GC、WebCodecs、OPFS、WebAuthn
- 2025 Web Almanac：移动端 **INP good 仅 77%，桌面 97%**；Top-1000 站点 INP 只有 63%。**越像 App 的站点越差**——这 20 个百分点正是小程序和 Skyline 绕开的那一层

## 07 · 四套可落地的组合

按起点而不是按理想选。每一套都标出了它的放弃项。

### A · 内容 / 交易型消费 App

要 Android + iOS + 鸿蒙 + 小程序 + H5，桌面可选

*移动*React Native + Expo（映射原生控件，跟得上 iOS 设计语言）

*鸿蒙*RNOH（华为 + Software Mansion，有小红书/携程生产背书）

*小程序*Taro（React 栈唯一选择）或原生小程序 + Skyline

*H5*Taro H5 输出

*桌面*Electron 或 RN Windows/macOS（后者落后主干 6 个 minor，慎用）

*放弃*UI 代码在小程序与 App 之间不复用，只复用 React 心智与部分逻辑

### B · 工具 / 企业 / B2B

表单密集、内部分发、迭代快、体验要求「不难用」而非「惊艳」

*全端*Capacitor + 一套 Web 前端

*鸿蒙*Capacitor 鸿蒙版（已适配 14 个官方 + 62 个三方插件）

*桌面*Electron（同一前端）或 Tauri（Windows/macOS 为主时）

*小程序*Taro 或 uni-app，另写一套

*放弃*动画流畅度、万级长列表、手写笔、连续 BLE。这些换来的是最低的人力与最快的迭代

### C · 已有 Android 团队，要低风险上 iOS

Android 侧已是 Jetpack Compose

*逻辑*KMP（Google 官方唯一背书的用法，Jetpack 里 iOS 是 Tier 1）

*UI*先各写各的；再逐屏评估要不要上 CMP

*桌面*Compose MP Desktop（复用同一套 UI）

*方法*抄 Booking.com 的 exit ramp：由 **iOS 工程师**定义验收标准（DX、部署、二进制体积、启动性能、调试、crash symbolication），写明达不到就用 Swift 重写，消除沉没成本压力

*放弃*CI 必须有 macOS runner；Firebase 官方 SDK 与 Dagger 没有 KMP 版

### D · 桌面为主，移动是附属

生产力工具、专业软件、内部平台

*Web 栈*Electron（要三端一致）/ Tauri（Windows+macOS，且无 WebGL 重负载）

*.NET 栈*Avalonia 12（唯一有 Linux AT-SPI2 无障碍的 .NET 框架）

*C++ 栈*Qt（先过授权闸门）

*移动*Capacitor 复用同一前端，或直接不做

*不要*为了「以后可能要移动端」而现在选 Flutter Desktop——它的桌面分支现由 Canonical 托管，纯桌面项目在为移动优先框架买单

## 08 · 不要强行跨端的地方

这些不是「跨端做得差一点」，而是所有跨端方案共同的硬边界。规划时直接划给原生。

#### 系统 UI 扩展

桌面小组件、Live Activity、锁屏组件、Apple Watch 独立 UI、App Clip、分享扩展、App Intents、Siri Shortcuts。**CMP 在技术上不可能**，Flutter / RN 官方文档都承认要写原生。

#### 后台长任务

后台定位、运动追踪、IM 保活、持续 BLE 连接。Sony 就是因为 BLE 后台执行不达标而放弃 RN。

#### 设备直连

蓝牙 / NFC / USB / 串口。iOS 的 H5 侧**零可能**——WebKit 已书面「决定不实现」。必须封成原生插件。

#### 高帧率交互

手写笔、绘图、白板、剪辑、游戏、图形编辑器。Capacitor 在 iOS 上 rAF 硬顶 60 fps 且 WebKit bug 一年无人认领。

#### 中文输入密集

IM、笔记、输入法。CMP 有三个 Open 的 Major 缺陷（删末字符、CJK 选择、交互式收键盘）；Flutter 也仍在修输入法长尾。**这一项必须在 POC 阶段亲手实测**。

#### 无障碍硬合规

政企 / 金融 / 医疗 / 教育采购。自绘路线在桌面走 MSAA、在 Web 走 canvas，都是明确短板。**.NET 侧只有 Avalonia 12 做了 Linux AT-SPI2。**

#### 端上 AI / 2D-3D 扫描

Shopify 在全量迁 RN 之后仍把这些明确列在「必须原生」清单里。

#### 跟系统设计语言走的品牌 App

要在 Liquid Glass 发布当季就跟上，自绘路线做不到——JetBrains 官方说要「native SwiftUI shell」，Google 说 Cupertino 要等解耦完成才能追。

**推荐的分层结构**（京东、小红书、美团、mPaaS 几边独立收敛到同一形态）：骨架与能力层原生——启动、路由、账号、支付、推送、音视频、设备能力、监控；业务页面跨端——占页面数和迭代量的约 80%；性能敏感页在同框架内走特殊路径。

## 09 · 排雷与数据缺口

这个领域的中文与英文内容里，过期案例和 AI 生成的伪数据都很密集。以下是本次调研中被证伪或需降级的说法。

| 常见说法 | 判定 |
|----|----|
| Airbnb 案例证明跨端不行 | **降级。**范围只有 220 屏（原生侧代码量约是其 10 倍），且 Airbnb 官方在 2026-07 给五篇 Sunsetting 文章顶部**全部加了声明**，大意是「如果这些文章被单独援引作为不要用 RN 的理由，请自行做更多研究」 |
| Marriott 从 RN 转回原生 | **证伪。**无任何一手来源，SEO 传说 |
| Udacity 整个 App 弃 RN | **失真。**只有 2 个功能 + 2 个原型，移除原因是功能本身要下线，**没有用任何东西替换** |
| 有公司放弃 Flutter 回归原生 | **三年窗口内穷尽检索，一例都没找到。**HN 全站相关查询 0 条 |
| BMW / eBay / 闲鱼 / 字节是 Flutter 活案例 | **过期。**官方 showcase 上这些页面内容全部停留在 2021 年。既不是撤退证据，也不能当现状证据 |
| Netflix / DoorDash 用 KMP | **过期 / 错误。**Netflix 一手来源是 2020-10；DoorDash 那条是**后端服务用 Kotlin** |
| Lynx 是自绘引擎 | **错误。**移动端映射原生控件，只有桌面 Clay 是自绘 |
| 「RN 0.74 让 Bridgeless 成为默认」 | **不准确。**0.74 是 ship（opt-in），0.76 才 by default，0.82 才 only |
| Tauri 比 Electron 内存低 58–75% 之类的具体数字 | **不可引用。**来源多为内容农场，引用的基准套件无法验证存在 |
| 小程序 setData 有 1024 KB 上限 | **已过期。**现行文档中找不到；官方口径已改为「组件 Shadow 树总节点量的影响大于数据量」 |
| 「符合 W3C MiniApp 标准」是加分项 | **不再是。**W3C MiniApps 工作组已于 2026-08-26 关闭，全部规范 Retired，原因是「no vendor has started to implement it yet」 |
| ArkUI-X 有大厂生产主干案例 | **未找到任何可信案例。**搜到的描述来源不可追溯，疑似 AI 生成 |

> ⚠️
>
> #### 最重要的负面发现：没有可信的跨框架性能实测
>
> **2024–2026 年间不存在可信、可复现、独立发布的跨框架性能对比**（滚动 FPS / jank / 冷启动 / 内存）。Flutter 的官方包体积数字**停在 2021 年 3 月**；RN 和 Capacitor 官方从不公布；CMP 唯一的「+9 MB」是 2025-05 的一个 demo，承诺发布的方法论至今未见，而 CMP-3632「减少 iOS 二进制体积」仍是 Open 状态。
>
> 唯一正确的做法是：**用你自己的真实应用，在你的目标硬件上，各出一个 PoC 实测。**Hello World 的对比对选型毫无价值。

- Reddit 全站、web.archive.org、微信公众号（闲鱼技术、字节跳动技术团队等中国大厂主发布渠道）、B 站与 YouTube 会议演讲
- 鸿蒙 2026 Q2 市场份额（只取到 Q1：中国 19%、全球 5%）
