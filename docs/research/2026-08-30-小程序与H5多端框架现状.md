> ℹ️ 最容易被忽略的一条
>
> **Taro 4.x 并没有推翻 Taro 3 的重运行时架构。**它在小程序端仍然是「逻辑层模拟浏览器环境 → 虚拟 DOM 树序列化 → setData」。4.x 的全部架构投入都花在了鸿蒙 C-API 上。如果你的诉求是「小程序端性能」，Taro 4 相对 Taro 3 **没有质变**。

## 03 · Taro 4.x 深读

### 没有 Taro 5.x

`@tarojs/cli` 的 `latest` 是 **4.2.1**（2026-07-17），另有 `4.2.2-beta.0`（2026-08-17）与 `4.2.2-alpha.1`（2026-08-24）；`v3-latest` 是 3.6.40（2026-04-13）。**npm 上不存在任何 5.x 通道。**

### Vite 是鸿蒙的入场券，不是小程序端的推荐项

- 同周 npm 下载：`@tarojs/webpack5-runner` 19,549 vs `@tarojs/vite-runner` 4,448 —— **Vite 采用率约 20%**。官方文档没有任何一处宣称 Vite 为推荐或默认。
- **Taro 的「Vite」是 Vite 4 + Rollup 3**：`@tarojs/vite-runner@4.2.1` 的 peerDependencies 写死 `vite: "^4"`，devDeps 是 `rollup ^3.29.4`。2023 年的工具链。
- 能力不对等：`prebundle`（依赖预编译）、Webpack5 持久化缓存、`logger` **都只有 Webpack5 有**。而持久化缓存 `cache.enable` **默认 false**（官方理由是「构建安全比构建速度重要」）—— 这是「Taro 编译慢」抱怨的一个制度性来源。
- Vite 模式的 open issue 密集：自定义 tabbar 不显示（[#18415](https://github.com/NervJS/taro/issues/18415)，webpack 无此问题）、`useShareAppMessage` 等 Hooks 失效（[#18745](https://github.com/NervJS/taro/issues/18745)）、cssModules 全局样式丢失（[#18698](https://github.com/NervJS/taro/issues/18698)）、`babel.config.js` 失效（[#18667](https://github.com/NervJS/taro/issues/18667)）、Vite 模板跑不通支付宝（[#18723](https://github.com/NervJS/taro/issues/18723)）。
- **鸿蒙端强制 Vite**：官方文档写死「当前仅支持使用 Vite 编译鸿蒙应用」。

### 鸿蒙 C-API：这是 Taro 4.x 唯一的架构突破

方案从 ArkTS 桥接升级为 **C-API**，把渲染管线整体下沉到 C++：

- ArkVM 层只剩业务代码 + React 核心 + 极薄 Taro 运行时；**TaroElement 大部分下沉 C++**，并在 ArkVM 层取消父子关系绑定。
- C++ 侧自研 CSSOM（解析 / 匹配 / 合成 / 应用全链路）+ 引入 **Yoga** 布局引擎对齐 W3C；`createSelectorQuery`、`createIntersectionObserver` 在 C++ 侧重写。
- 基于鸿蒙 VSync 建任务管线；长列表用 `NodeAdapter` 实现懒加载 / 预加载 / 组件复用（`reuseId`）。
- 支持与鸿蒙原生组件混合渲染。

**京东公开的数字（厂商自述）：**首页渲染 1062ms（较 ArkTS 版 +23.9%）、商详 560ms（+74.2%）；长列表优化后页面加载与更新平均 **+38%**、首页内存占用 **-54%**。京东 App 纯血鸿蒙版 2024-09 上线即获华为 S 级认证。

> ⚠️ 承诺与落地的差距
>
> 官方 2025-04 称多线程架构「正在试点接入，很快正式上线」，2025-05 称多线程升级与 **React 的 C++ 化**「处于验证和测试阶段」。但 **4.1.0 与 4.2.0 的 release note 中均无相关记录**（4.1.0 反而是「单线程音视频策略调整」），4.x 鸿蒙文档侧边栏也没有多线程章节。⚪ 截至 4.2.1，多线程架构与 React C++ 化是否 GA：不确定，倾向未 GA。

### Taro React Native：按不可用处理

官方从未宣布弃用，但六条独立证据交叉指向冻结：

- 官方兼容表**最后一行是 RN 0.70.x**，而 `@tarojs/rn-runner@4.2.1` 的 peerDeps 钉死 `react-native ^0.73.1 / expo ~50.0.0`；`4.2.2-beta.0`（2026-08）依旧。社区 RN 已到 0.87。
- RN 0.76 + Expo 52 的适配 2024-11 就做进了 `4.0.7-canary.6`，到 2026-08 **仍卡在 canary，连 beta 都没进**。
- 官方脚手架 + 官方默认模板，**第一条 RN 命令就跑不通**：[#19486](https://github.com/NervJS/taro/issues/19486)（2026-08-22 创建，至今 0 回复）。
- `label:T-rn` issue 共 403 个，open 155 个（38.5%）；`@tarojs/rn-runner` 周下载 1,000，仅 webpack5 通道的 5.1%。
- 官方博客最后一篇 RN 专题是 **2021-10-14**。搜 `Fabric / TurboModule / new architecture` 无任何讨论。

### 其他硬约束与坑

- **React 停在 ^18**，Preact ^10，Vue3 ^3；**无 Solid**。首页展示了 Svelte logo 但 `framework` 枚举不含 svelte ⚪ （矛盾，按不可用判断）。
- **包体积的架构性来源**（官方自陈）：小程序组件属性必须静态写死，Taro 把 `View` 的**全部属性和事件都提前绑进模板**，「循环这些冗余的属性和事件绑定也会占据很大一部分的体积，另外太多的事件绑定也会在一定程度上降低小程序的性能」。
- 多端样式差异的官方口径：「样式布局上 H5 最为灵活，小程序次之，**RN 最弱**」。RN 端仅类选择器、无伪类伪元素、View 默认主轴 column、不支持 `background-image`。
- Vue `scoped` 在 H5 生效、微信小程序无效（[#6662](https://github.com/NervJS/taro/issues/6662)，长期 open）。
- **文档与制品严重脱节**：`compiler` 默认值文档仍写 `webpack4`（4.x 已无该通道稳定制品）、showcase 数据停在 3.6.7、harmony-hybrid 文档停在 HarmonyOS NEXT Preview1、官方博客自 2025-05-16 停更、**4.0/4.1/4.2 都没有正式发版博客**。选型请核对 npm peerDependencies，不要只信文档。

> 🔴 谣言排雷
>
> issue [#19468](https://github.com/NervJS/taro/issues/19468)「Taro 已支持 Vite 8, React 19, Tailwind 4」**不是官方公告**，作者是社区用户，推广的是第三方项目 `vite-plugin-taro`。如果你在别处看到「Taro 已支持 React 19」，很可能就是这条被误传。

## 04 · uni-app x 与蒸汽模式

### 这是一次战略掉头，不是版本迭代

理解 uni-app x 必须分清两代：

|  | VDOM 模式（第一代，2023–） | 蒸汽模式 Vapor（2026 起） |
|----|----|----|
| 编程语言 | **UTS** —— 编译为 Kotlin / Swift / ArkTS / JS | **回到普通 ts/js**；UTS 退居原生插件（utssdk 目录） |
| 渲染 | 虚拟 DOM + 原生渲染，**实测比原生慢**（官方自述） | 去掉 VDOM + **全新自研原生 UI 框架** |
| 视图层产物 | 编译为 uts/js 驱动原生渲染 | `template` 与 `style` **直接编译为 C 代码 → 机器码/字节码** |
| 组件实现 | 各平台各写一套（Android 用 RecyclerView、iOS 用 UICollectionView） | **一套 C/uts 跨平台实现**，几乎不用系统组件 |
| 上线时间 | — | 鸿蒙 HBuilderX 5.0 / iOS 5.11 / Android 5.21 |
| 最低系统 | Android 5 / iOS 12 / 鸿蒙 API 14 | **Android 6 / iOS 15 / 鸿蒙 API 20（鸿蒙 6.0+）** |

来源：[uni-app x 介绍页](https://doc.dcloud.net.cn/uni-app-x/)、[蒸汽模式文档](https://doc.dcloud.net.cn/uni-app-x/app-vapor.html)（均 2026-08 更新）。

DCloud 对掉头原因的解释值得原样理解：**UTS 的价值在于消除跨语言通信折损；蒸汽渲染引擎做好后，把这个折损压到 5% 以内，而渲染本身已快出 2–3 倍，5% 就不重要了** —— 于是换回 JS，换来动态性、生态、AI 友好度和老用户迁移路径。

### 官方 benchmark（DCloud 自测，但原生对照源码全部开源可复现）

| 测试项 | 平台 / 设备 | 原生 | uni-app x 蒸汽 |
|----|----|----|----|
| 4050 个 view+text · 同屏创建（ms，越低越好） | Android 小米 Fold4 | 原生 View 461.8 / Compose 625.8 | **229.2** |
|  | iOS iPhone SE2 (26.5) | UIKit 329.4 / SwiftUI 385 | **158.2** |
|  | 鸿蒙 nova12 (API21) | ArkUI 798 / NativeNode 672 | **280** |
| 「死亡长列表」 · 4000 行 / 7.4MB JSON / 2 万元素 · （平均帧率，越高越好） | Android 小米 Fold4 | 原生 View 45.35 / Compose 51.09 | **109** |
|  | iOS iPhone 16PM 高刷 | SwiftUI 49 | **111** |
|  | 鸿蒙 nova12 | ArkUI 21.13 | **97.97** |

原生对照源码：[test4050-android](https://gitcode.com/dcloud/test4050-android)、[-ios](https://gitcode.com/dcloud/test4050-ios)、[-harmony-arkui](https://gitcode.com/dcloud/test4050-harmony-arkui)、[AndroidDeadlyList](https://gitcode.com/dcloud/AndroidDeadlyList) 等。DCloud 明确要求 release 包测试。这些数字应视为厂商自述，但**可复现性远高于行业平均**。

技术上说得通的部分：Compose UI 也是基于原生渲染管线但自研排版与组件系统，实测比 View 体系慢 —— 说明「基于原生渲染管线 + 自研 UI 框架」这条路本身可以做得更快或更慢，关键在实现。uni-app x 声称几乎不用系统的 TextView / RecyclerView / ArkUI 组件，并把视图层编译成机器码/字节码。

### 代价清单（迁移前必读）

- **仅支持组合式 API，不支持选项式；不再支持 mixin。**存量 uni-app 选项式代码需全量改写。
- **CSS 运行时不支持复杂关系选择器**，只支持简单 class 与分组选择器 —— 必须改 BEM。
- **样式隔离策略 2.0**：组件默认不受外部同名 class 影响（含全局 CSS），需显式 `styleIsolation`。三方组件必须支持 2.0 才能用。
- Android 端 uvue 页面**不能直接调原生 API**（含 `utsAndroid`），须挪到 uts 插件。
- `list-view` 复用规则严苛：`list-item` 的 `v-for` 必须有 `:key`；只有第一组 `v-for` 复用；`list-item` 必须与 `list-view` 写在**同一个 uvue 文件内**；不支持横向滚动；不支持 margin。
- `flatten`「拍平」是性能关键，但拍平后**不支持事件、截图 API、visibility、z-index、background-image、pointer-events**，gif/webp 只显示第一帧；鸿蒙上还要求**至少两个相邻元素同时拍平**才有收益，否则反而变慢。
- **打包后目前不能热更新**（开发期可热刷）；蒸汽模式的 wgt 热更新「暂未上线」。
- 机器码 vs 字节码：字节码性能低约 3%，但编译快、支持差量与热更新。iOS/Android 上**只提供字节码**（机器码云打包太慢）。
- App 平台 CSS 是 Web 子集；文字必须写在 `text` 内且样式不继承；默认 flex 竖向。

### 小程序端的实际差异

uni-app x 编译到小程序**仍以 VDOM 模式运行**（蒸汽未覆盖）。相对老 uni-app 的两处显著差别：

- 提供跨平台 **Element API**，在微信端映射到 `wxs` —— 解决了 wxs 难用且不跨平台的问题。但小程序端 `UniElement` 只支持 `id / nodeName / tagName / style / getBoundingClientRectAsync / getAttribute`。
- **全平台统一 flex 布局**，并默认启用 `virtualHost` + `mergeVirtualHostAttributes`（只合并 id / style / class / hidden 四个属性，且仅单根节点组件），这会改变真实渲染的 DOM —— **尤其影响在组件外获取组件 DOM**。
- 对 Skyline 的支持**处于实验阶段**；worklet 函数暂不支持写在 uvue/uts 文件内。
- 官方基线：微信基础库需 **\> 3.7.1**，否则 `scroll-view` 区域大小不准。

> 🔴 生产验证的真实水位
>
> DCloud 在案例页原文写道：「**由于 uni-app x 没有运行时数据采集，所以 DCloud 并不知道哪些开发者在真实使用 uni-app x**」，并呼吁大型开发者主动提 PR 贡献案例。公开案例列表以工具、OA、教育、政务、物联网类中小 App 为主，且以鸿蒙端居多，**明确标注为蒸汽模式的仅 2 个**（发票匣、仪表宝典）。这与 Taro 拿京东 App 核心购物链路做背书，是完全不同的验证强度。

### Mpx 值得单独说：它是另一个物种

Mpx **不是「更好的 Taro」**。它的源码 DSL 是**增强版微信小程序语法**（`wx:class` / `wx:style` / `wx:model` / `wx:ref` / `wx:show` / 动态组件），不是 React 也不是 Vue SFC。官方自己做了三分法定位，原文：

> 一类是以 uniapp、taro2 为代表的**静态编译型**框架……另一类是以 kbone、taro3 为代表的**运行时框架**……由于模拟的 web 运行时环境带来了巨大的性能开销，这类框架**并不适合用于大型复杂的小程序开发**。不同于上面两类框架，Mpx 以小程序本身的 DSL 为基础……**没有复杂庞大的转译和环境抹平**。

运行时机制：MobX 做响应式，模板编译为 render 函数做依赖收集，异步队列保证一个 tick 最多一次 `setData`，并按**数据路径**与上次数据 diff 后增量下发。运行时体积官方称 51KB（介绍页）/ 压缩后 60KB（首页）⚪ 两处口径不一。

**选它的理由：**小程序端性能与包体积最优；能直接用 vant/iview 等原生组件库；2026 年在 RN（含鸿蒙）方向投入很猛。**不选的理由：**存量 React/Vue 代码无法平移；生态规模仅 Taro 的 1/12（forks 388 vs 4,871）；**核心维护高度集中于一人**（hiyuki 4,910 commits ≈ 第 2–9 名总和，且是 release author 与主要 publisher）；缺快手/京东/钉钉/淘宝端。

### 2024–2026 出现的新东西

- **Lynx（字节）** —— 2025-03 开源，15,009 star，活跃。但**产物是原生 App UI，不输出小程序**，不是 Taro/Mpx 的替代品，选型时不要混为一谈。
- **Kuikly（腾讯 TDS）** —— 2025-04 开源，3,417 star，2026-08-27 仍活跃。基于 Kotlin Multiplatform，官方 2026 Roadmap 明确 **H5 与微信小程序均为 Beta，2026 目标转正式 Release**。源语言是 Kotlin，对前端团队是完全的技术栈切换。2026-08 不适合作为小程序主方案。
- **Rust 系小程序编译器**：未发现全新项目。Rust 以工具链形式进入既有框架（Taro 用 SWC wasm 插件 + Rust 工具预计算样式）⚪ 是否存在未检索到的方案：不确定。

## 06 · Skyline 与 glass-easel

### Skyline 已 GA，但「GA」不等于「默认生效」

引擎迭代到 **1.4.22（2026-08-26）**，月度更新节奏，文档无 beta/实验标记。最低版本：微信 Android/iOS **8.0.40**（基础库 3.0.2）、微信鸿蒙 OHOS **1.0.10**（基础库 3.11.3）。

> 🔴 最容易踩的坑（官方自己加粗的一句）
>
> 「**由于 Skyline 默认接入 We 分析的 AB 实验，未配置的情况下，页面渲染仍为 WebView 引擎**」。而且「当 AB 实验的流量分配到 100% 时，**并不代表是全量，而是 Skyline 和 WebView 各 50%**」。要绕开需显式配置 `rendererOptions.skyline.disableABTest: true` 并给出 `sdkVersionBegin/End`。

### 架构上到底改了什么

不是「移除了双线程」，而是换了切法：原来是「逻辑层 JS 线程 ↔ 渲染层 WebView（JS + 排版 + 绘制混在一起）」，现在是「**AppService 线程（逻辑 + 建树 + WXS）↔ 渲染线程（Layout / Paint / Composite，无 JS）**」。官方列出的收益：

- **「框架的代码之间无需再通过 JSBridge 进行数据交换」** —— 跨线程序列化环节被消掉。
- 无需为每个页面新建 WebView 实例，页面间可共享资源。
- **同步光栅化**（WebView 是异步分块），消除快速滚动白屏与滚动中 DOM 更新不同步。
- view/text/image 等内置组件**从 JS 下沉到原生实现**（创建开销 -30%）。
- WXSS **预编译为二进制**，运行时直接读（比运行时解析快 5 倍以上）。
- 默认启用 glass-easel，建树耗时 **-30%~40%**，且 **setData 调用不再有通信开销和序列化开销**。

官方性能数据（取自微信自家「小程序助手」线上）：**首屏时间比 WebView 快 66%**；内存单页 **-35%**、双页 **-50%**，页面越多差距越大。

⚪ Skyline 的布局引擎实现（是否 Yoga / Flutter）官方文档未提及，社区「基于 Flutter」的说法未找到官方佐证。

### 兼容性代价：这是决定能不能上的关键

| 类别 | Skyline 下不支持 / 行为不同 |
|----|----|
| 布局 | **无 inline 布局**（开发中）、inline-block 仅 text 内嵌套、**没有 BFC**；`display` 只有 none/flex/block 且**默认 flex**；`box-sizing` 默认 border-box |
| 滚动 | **`overflow: scroll` 不支持**，滚动只能用 `scroll-view`（且需显式 `type="list"`）；不支持 `overflow-x/y` 单独设置；**不支持 `position: sticky`**（改用 sticky-header / sticky-section 组件） |
| 选择器 | 无通配符 `*`、无属性选择器 `[attr]`；伪元素只有 `::before/::after`；`:nth-child` 需 8.0.50 |
| 属性 | `z-index` **不支持层叠上下文，只对兄弟节点生效**；`box-shadow` 不支持多个叠加；`background-image`/`mask-image` 不支持多张；`text-overflow`/`text-decoration-*` 仅作用于 text 节点；`border-*-color` 默认 black 而非 currentcolor |
| 单位 | **`em` 不支持**；Media queries **只支持 DarkMode**；Font-face **只支持 ttf** |
| 组件 | **`web-view` 不支持**（该页需单独配 `renderer: "webview"`）；`movable-area/view`、`editor`、`progress` 不考虑；`xr-frame` 暂未支持；**只能用自定义导航**（`navigationStyle: custom`）；内联文本只能用 `text`，混排要用新增的 `span` |
| 交互 | 动画与手势**必须写 worklet**（`'worklet'` 指令 + `runOnUI` + `shared` 共享变量）；WXS 在 Skyline 下运行在 JS 线程，**已不是动画方案**；手势组件是虚组件，不冒泡，仅一个直接子节点，回调必须是 worklet |
| 平台缺口 | **Windows / Mac 端与企业微信仍在「规划中」** |

来源：[Skyline WXSS 文档](https://developers.weixin.qq.com/miniprogram/dev/framework/runtime/skyline/wxss.html)、[组件差异](https://developers.weixin.qq.com/miniprogram/dev/framework/runtime/skyline/component.html)、[特性状态](https://developers.weixin.qq.com/miniprogram/dev/framework/runtime/skyline/status.html)。

好消息是**可以按页面或分包粒度混用**，Skyline 页面与 WebView 页面可混跳，不支持的版本自动降级 WebView。但降级矩阵里有两项**明确不兼容**：`scroll-view` 新增属性与事件、`sticky-section/header`。

### glass-easel：组件框架，不是「小程序脱离微信」

- MIT 开源，[wechat-miniprogram/glass-easel](https://github.com/wechat-miniprogram/glass-easel)，npm **1.1.0（2026-08-28）**，961 commits，**极活跃**。TypeScript 59% + Rust 29%（模板与样式编译器是 Rust 写的）。
- Skyline 下**强制使用** glass-easel；WebView 渲染自基础库 **3.8.12** 起也可用，但需**同时写两个字段** `componentFramework: "glass-easel"` + `glassEaselWebview: true`（只写前者可能只激活编译器不激活运行时）。
- 带来的算法收益：**绑定映射表更新**不需要遍历组件树，靠编译期信息直接定位数据绑定表达式（条件：单独更新一个字段，且该字段未用于 `wx:if/wx:for/let:`）；独有 `updateData` / `groupUpdates` / `spliceArrayDataOnPath`，官方称「性能显著优于多次调用 setData」。
- **但它跑不了小程序内置组件。**README 原文：「这个模块只是组件框架本身，而不包含 `<view />` `<image />` 等小程序组件实现……**不能将小程序的组件代码直接复用到 web 环境下**」。所以它是「自定义组件代码复用」，不是「小程序脱离微信运行」。

**与跨端框架的衔接：**Taro 4.x 官方支持 Skyline，但仅微信端，worklet 需 **4.0.8+** 且**必须开启半编译模式**（`mini.experimental.compileMode = true`）。uni-app x 的小程序端对 Skyline 支持处于**实验阶段**。

### setData 现状的一个重要更新

官方现行口径已经转向：**「影响数据更新方法性能的因素主要有：1. 组件 Shadow 树总节点量；2. 更新的数据量。其中，前者的影响比后者更大。」**—— 从「数据量为主」改成了「**节点数比数据量更要命**」。

> ⚠️ 别再引用的那个数字
>
> 广为流传的「setData 单次不能超过 1024KB」⚪ 在 2026 年现行官方文档中已找不到（Page.html 重构后不再含 setData 章节，组件脚本页与 runtime_setData 页均无该表述）。同样，「转成字符串拼 JS 脚本执行」这句经典描述**也不是现行官方原话**，只见于社区二手文章。写进决策文档前请自行核实。

## 07 · 为什么 RN / Flutter 到不了小程序

小程序不是「受限的浏览器」，而是**一个不交出渲染树、不交出 JS 引擎句柄、不执行原生二进制、且禁止动态执行代码的沙箱**。RN 与 Flutter 各自依赖的宿主能力，恰好落在这四条禁令上。

### 四条根本禁令

| 禁令 | 官方依据与后果 |
|----|----|
| 禁止动态执行代码 | 官方原文：「基于安全考虑，小程序中不支持动态执行 JS 代码，即：不支持使用 `eval`；不支持使用 `new Function` 创建函数（`new Function('return this')` 除外）」。→ 一切「运行时下发 / 生成代码」的退路被封死。 |
| 逻辑层无 DOM/BOM | 官方原文：「小程序框架的逻辑层并非运行在浏览器中，因此 JavaScript 在 web 中一些能力无法使用，如 `window`、`document` 等」。→ **无法同步测量元素**，布局信息只能走异步 `SelectorQuery`。这正是 RN 的 Yoga 同步文本测量回调、Flutter 的同步布局都落不了地的同一个根因。 |
| 视图层不跑开发者 JS | WXS「与 JavaScript 是不同的语言，有自己的语法」，与逻辑层隔离，不能调 JS 文件的函数，也不能调小程序 API。 |
| wasm 不能从字节流实例化 | `WXWebAssembly.instantiate(path, imports)` 的 **path 必须是代码包内路径**（.wasm / .wasm.br）；export 支持函数/Memory/Table，**iOS 不支持 Global**；无 WasmGC、无共享内存多线程。→ 标准的 `fetch → instantiate(buffer)` 路径不成立，wasm 必须打进代码包**强制吃配额**。 |

### 包体积硬顶（选型算账用）

| 平台 | 主包 | 单分包 | 总计 |
|----|----|----|----|
| 微信 | 2M | 2M | 30M（服务商代开发 20M） |
| 支付宝 | 4MB ⚪ 另一页写 2MB，官方矛盾 | 4MB | 20MB |
| 抖音 | 4M（文档注明未来降到 2M） | 2M | 16M |
| 百度 | ⚪ 未能获取（文档站为 SPA 空壳，抓取超时） |  |  |

架构设计请按最严的口径（主包 2M）对齐。

### React Native：Fabric 需要的四样东西小程序一样都没有

- RN 新架构的 fiber「stores a **C++ pointer** to the React Shadow Node, **made possible by JSI**」；JSI 的定义是「把 JS 引擎**嵌入一个 C++ 应用**的轻量 API」。→ 小程序的引擎归微信客户端持有，业务代码只是被喂进去的脚本，**拿不到引擎句柄**。
- Mount 阶段把变更施加到**平台原生 View**（`<View>` → `android.view.ViewGroup`，`<Text>` → `android.widget.TextView`）。→ 小程序视图层只接受 WXML 模板 + setData，**不存在可被第三方实例化的原生 View 类型**，Mount 没有落点。
- Codegen 产出 C++ glue + Java + Objective-C++，「every time an **iOS or Android app is built**」。→ 小程序代码包**没有加载 .so 的入口**。
- Yoga 对 Text/TextInput 的布局会「invokes a function defined in the **host platform**」—— **同步**测量回调。→ 小程序测量 API 全异步。

**试过的人：**携程系 [Alita](https://github.com/areslabs/alita) 用编译期方案（JSX 片段编号成 template，改写 `ReactDOM.render` 收集 uiDes 再 setData），最后 release 2020-05，且官方未实现清单里**`NativeModules` 就在其中** —— 等于整个 RN 原生生态出局。Remax 是真运行时 React，已归档。**未发现任何在小程序中运行 Fabric/JSI/Yoga 的项目。**

### Flutter：算一下就知道塞不进去

- Flutter Embedder 的职责是「coordinates with the underlying OS for access to services like **rendering surfaces, accessibility, and input**; and manages the **message event loop**」，Release 模式「compiled directly to **machine code**」。宿主必须交出：可写 GPU surface + 原始事件流 + 能执行机器码的运行时 + 事件循环控制权。
- Flutter Web 现在只剩两个 renderer（html renderer 已从文档消失）：**canvaskit「adds about 1.5MB」**（需 WebGL），**skwasm「adding about 1.1MB」**（需 **WasmGC**，多线程需 **COOP/COEP** 跨源隔离，且官方 warning：「Flutter compiled to Wasm **can't run on the iOS version of any browser**」）。
- 把这两个数字放进上表：**光渲染引擎就吃掉微信 2M 主包配额的约 3/4**。skwasm 路线还被 WasmGC、跨源隔离头、iOS WebKit 三重独立否决。

**唯一跑通的是 [MPFlutter](https://github.com/mpflutter/mpflutter) 2.0**：Flutter Web(dart2js) + 定制 CanvasKit（经 WXWebAssembly 加载）+ `<canvas type="webgl">`，JS 只接收最基本触摸键盘事件后交回 Flutter Framework。为塞进 2M 做的事本身就是成本证据：内置 brotli、自研 MiniTex 文本渲染器绕开 Skia 字体栈、做**无字体渲染能力的定制 CanvasKit 产物**、main.dart.js 分包「默认不大于 700K」。**状态：2,144 star，最后 push 2025-03-25（约 17 个月），且 2.0「并不是一个完全开源的项目」，商用需购买授权。**一个必须紧跟 Flutter engine 定制 CanvasKit 的项目停更 17 个月，基本等于停摆。

另注：Kraken/北海方向相反 —— 它是「用 Flutter 当渲染后端跑 W3C 标准」，与小程序无关；继任者 WebF 的目标平台列表里**没有小程序**。

## 08 · 小程序容器：能与不能

> 🔴 先纠正两个普遍误解
>
> **①「接入容器就能接入微信小程序生态」不成立。**FinClip 这类第三方运行时兼容的是**微信语法**，跑的是「用微信语法写的、上传到你自己平台的」小程序，**跑不了微信线上的小程序**。真正能跑微信线上小程序的只有 WMPF，而 WMPF 登记页明文写着「**WMPF 不支持在手机、PC 等通用型设备上运行**」。
>
> **②「容器 = 跨端」要打折。**FinClip 鸿蒙端能力明显晚于双端且**无官方差异清单**；mPaaS 鸿蒙端官方列了 5 类不支持 API；FinClip 的 `Canvas.createImageData/toDataURL` 备注「**目前仅 iOS 支持**」。

| 方案 | 运行时 | 微信语法 | 鸿蒙 NEXT | 当前状态（2026-08） |
|----|----|----|----|----|

### 代价，按证据排序

1.  **能力天花板锁死在容器暴露的 API（不可谈判）。**FinClip 官方 API 总览逐条列出「暂未支持」：**Skyline 全家桶**（含 worklet、自定义路由、preloadSkylineView）、半屏小程序、**日志与性能上报**（`getLogManager`/`getRealtimeLogManager`/`reportPerformance`）、mDNS、`Canvas.createPath2D`；`live-player/pusher` 需另接三方音视频 SDK，`map` 需另接地图 SDK。mPaaS 鸿蒙侧 canvas2、直播、文件 API、联系人全不支持。
2.  **版本碎片是三维的**：宿主 App 版本 × 容器 SDK 版本 × 基础库版本，再 × 端。FinClip 的版本对照表只覆盖 iOS/Android 且只到基础库 3.0.1 ↔ SDK 2.37.1（当前 3.12.4 / 2.53.7），鸿蒙/桌面/Flutter/RN 完全没有对照关系。
3.  **包体积的真实成本远高于宣传。**FinClip 文档「核心 SDK 体积仅 1MB 多一点」不含 5 个 ABI 的 `libsdkcore.so`、不含 Kotlin stdlib/gson/zxing、不含任何扩展 SDK；一旦要 WebRTC，官方自己说「体积最多增大 6.2MB」。厂商两处自述还打架（CocoaPods README「不超过 2M」vs Gitee「less than 3MB」）。DCloud 给的 7MB/16MB 更接近真实量级。**PoC 第一件事就是量 APK/IPA/HAP 增量。**
4.  **调试链路变长**：多进程意味着崩溃栈、日志、断点都跨进程；而 FinClip 不支持微信生态成熟的日志与性能上报 API，线上监控要在宿主侧重建。
5.  **性能：整个赛道不公布可比数据。**FinClip 与 mPaaS 官方文档里**都没有任何启动耗时、内存、FPS 基准**，只有「媲美原生」「秒开」。这个信息真空本身就是判断依据。
6.  **供应链风险。**FinClip：podspec 写 `license: Copyright`、`libsdkcore.so` 是加固过的 native 库、**Maven Central 零结果**（Android 制品锁在需口令的私有 Nexus）、社区版**有 2027-03-31 截止日期**且不支持保数据升级、主体已变更为深圳泰坪科技。mPaaS：mPaaS 内核 **42,000 元/应用/年**，且容器正从 Nebula 换代到 MRiver。

> ⚠️ 一条本月刚变的事实
>
> **W3C MiniApps 工作组已于 2026-08-26 关闭**，全部规范列为 Retired。提案人自己记录的原因是「There are vendors interested in implementing, but **no vendor has started to implement it yet**」。「符合 W3C MiniApp 标准」从此不再是选型加分项 —— 但部分厂商官网页脚仍挂着该工作组成员资质图标。

### 什么时候合理

✅ 合理 金融/政务/央国企的超级 App 生态化（宿主自有且用户量大、需引入外部服务方又不能让对方进主工程、发版受管控但业务要快、有预算做私有化）—— 银行券商是全部客户画像，这不是巧合。✅ 合理 多 App 复用业务模块。✅ 合理 动态化发版与灰度。✅ 合理 专用硬件（POS / 点餐屏 / 自助机 / 车机）跑真微信小程序 —— WMPF 唯一成立的场景。

🔴 不合理 核心业务主链路（交易、支付、开户、行情）—— 等于把自己的天花板交给厂商排期。🔴 不合理 只是想让 web 团队并行交付页面（Capacitor 或自建 WebView 容器就够）。🔴 不合理 单 App、小团队、无生态诉求 —— 容器的价值在「多方协作」与「发版解耦」，只剩热更新时有更轻的方案。

**第一分叉点：能否动态下发第三方代码。**需要，才谈容器；不需要，编译期方案在性能、体积、调试上全面占优（DCloud 自己都在 uniMP 文档里引导用户走 uni-app x 原生 SDK：iOS +8.7M / **鸿蒙 +1MB** / Android +8.1M，代价是失去运行时动态下发）。

## 09 · H5 的能力边界

基线：**Safari 26.6 / iOS 26.6**（2026-07-27 发布），Safari 27 仍在 beta。Apple 已改用年份版本号。

> 🔴 对本次选型影响最大的一条
>
> **iOS 的 WKWebView 里 Service Worker 完全不可用**（MDN BCD 明确 `webview_ios: false`，而 `webview_android` 有）。连带 **Web Push 在 WKWebView 里也是 false**，且存储配额只有磁盘的 **~15%**（浏览器与主屏 web app 是 ~60%）。也就是说：**「H5 在浏览器里」和「H5 在你自己 App 的 WebView 里」在 iOS 上是能力完全不同的两个东西。**设计前必须先确定 H5 跑在哪 —— 这正是小程序容器与离线包机制存在的理由。

### iOS PWA：唯一可靠形态是「添加到主屏幕」

- **ITP 7 天清除仍然存在**：用户 7 天无交互，删除全部 script-writeable storage —— IndexedDB、LocalStorage、SessionStorage、**Service Worker registrations and cache**。
- **但主屏幕 web app 豁免**：官方原文「The first-party domain of home screen web applications is **exempt from ITP's 7-day cap**」，且数据与 Safari 隔离。同时拿到 ~60% 磁盘配额，`persist()` 的启发式也把「是否作为主屏幕 web app 打开」计入。
- **Web Push 自 iOS 16.4 起支持，但至今仍要求「添加到主屏幕」**（BCD 注：Notifications are supported in web apps saved to the home screen）。未找到任何「普通 Safari 标签页可订阅」的官方来源。
- **`beforeinstallprompt` 在 Safari 全线不支持**，安装引导只能自己画。
- 后台同步 / 周期同步 / Background Fetch：**iOS 全部为零**（仅 Chrome/Edge）。
- 欧盟第三方浏览器引擎（iOS 17.4+）需申请 entitlement，且必须做**仅限欧盟发行**的独立版本。⚪ 是否已有厂商实际上架：不确定。对中国/全球市场应按「零影响」规划。

### 性能：INP 是移动端真正的短板

HTTP Archive Web Almanac 2025（CrUX 真实用户数据）：

| 指标（2025）             | 移动 good | 桌面 good |
|--------------------------|-----------|-----------|
| Core Web Vitals 全部达标 | 48%       | 56%       |
| LCP ≤ 2.5s               | 62%       | 74%       |
| INP ≤ 200ms              | 77%       | **97%**   |

关键在分布：移动端 INP 达标率按流量排名分段是 —— Top 1,000 **63%**、Top 10,000 56%、全站平均 77%。**越像 App 的站点越差。**首页 INP good 80%，**二级页跌到 69%**（2024 年两者还基本持平）。Almanac 的归因是电商、社交、新闻门户天然需要更多 JS 执行。

这 20 个百分点的移动-桌面差距，本质就是移动 CPU 上的 JS 主线程执行时间 —— **正是小程序用「逻辑层-渲染层分离 + 原生组件」、Skyline 用「消除 JSBridge 序列化 + 组件下沉原生」绕开的那一层**。

⚪ WKWebView 是否与 Safari 享有同等 JIT：本次未能用官方来源证实。可确认的只有：iOS 的 JIT 由 Apple 专有 entitlement 把守，Safari 用它跑 JS JIT；锁定模式会关闭 JIT。工程上应真机跑 Speedometer 对比 Safari 与自家 WebView。

## 10 · 原生多写几套的真实成本

差异不是「前缀不同」，而是三套心智模型：**微信 ↔ 抖音 ≈ 同构；任意一端 ↔ 支付宝 = 全线不同**。

| 维度 | 微信 | 抖音 | 支付宝 |
|----|----|----|----|
| 事件绑定 | `bindtap`/`catchtap`/`capture-bind` | 同微信，另有 `bind:tap.stop/.capture` | `onTap`/`catchTap` —— **驼峰事件名** |
| 长按阈值 | — | `longpress` **350ms** | `longTap` **500ms** |
| 组件模型 | `properties`(type/value/observer) + `behaviors` | 同微信 | **`props`（直接给默认值）+ `mixins`** |
| 生命周期 | `created/attached/ready/moved/detached` | 同微信 | `onInit`/`deriveDataFromProps`/`didMount`/`didUpdate`/`didUnmount`；需启用 component2 |
| 渲染层脚本 | WXS，CommonJS | 名为 SJS 实为 WXS，CommonJS | **SJS 用 ESM**，`export default` + `<import-sjs>` |
| 独立分包 | ✅ 支持 | ✅ 支持 | 🔴 不支持 只有 root/pages |

### 真正的坑是同名 API 语义不同（静态检查抓不到）

- 抖音的 `selectComponent`/`selectAllComponents` 是**异步、必须传 callback**，微信是同步返回 —— 直接搬代码拿到 undefined。
- 事件对象结构不同：支付宝 `event.target` 有独有的 `targetDataset`；抖音 tap 事件带 `detail:{x,y}` —— 微信里读 `event.detail` 的逻辑搬到支付宝直接 undefined。
- 能力粒度不同：`my.scan` vs `wx.scanCode`；`my.setNavigationBar` 单 API 统管 vs 微信多个 API；日期选择支付宝是 API（`my.datePicker`）而微信是组件（`<picker mode="date">`）。

### 转换工具：真正的「转换器」已死

antmove 已由作者明确宣布停止维护（README 第一行）；MorJS 架构上对路但 release 停滞 15 个月、月下载 368。**活下来的全是「统一 DSL + 条件编译」路线**（Taro / uni-app / Mpx）。

而框架厂商自己也承认抹不平 —— Mpx 的跨端矩阵直接列出：抖音端**不支持** `wx:class`/`wx:style` 动态样式增强、`computed` **无法作为 props 传递**、分包增强不可用，并明说「对于一些无法进行模拟的跨平台差异，会在运行时进行检测并报错指出」。

> ⚠️ 关于「多写一套增加 N% 工作量」
>
> **没有找到任何公开的、可核实的量化数据。**所有能找到的都是定性宣传：MorJS「节省双倍人力」、Chameleon「成本成倍增加」、Taro「成本显然非常高」—— 无一含测算依据。**任何百分比数字都属无来源，不要写进决策文档。**若必须量化，建议用可核实的硬约束做内部估算：2M vs 4M 的包体积差、上表的 DSL 差异条目数、抖音的三处能力洞、支付宝的组件模型重写量。

## 11 · 适合与绝对不适合

### 先走这四个分叉点

*Q1*需不需要向端上动态下发第三方代码？

**需要** → 只能走小程序容器（FinClip / mPaaS），并接受第 08 节的全部代价。**不需要** → 编译期方案在性能、体积、调试上全面占优，直接跳过容器。

*Q2*App 端的渲染体验是不是核心竞争力？

**是** → Taro RN 通道已冻结，不要选；只剩 uni-app x 蒸汽模式（新，但 benchmark 强且可复现）或纯原生。**否（App 只是壳 + 少量原生能力）** → 三家都行，选生态。

*Q3*要不要鸿蒙 NEXT？

这是 2026 最大的分水岭。**要** → Taro（C-API，京东生产验证最强）或 uni-app x（蒸汽首发平台，但要求 API 20+ / 鸿蒙 6.0+）。**不要** → 选择面立刻宽很多，Mpx 也进入候选。

*Q4*存量代码是 React 还是 Vue？

**React** → Taro 是唯一选择（但停在 React 18）。**Vue** → Taro / uni-app / uni-app x 都行。**绿地项目且以微信为绝对主战场** → Mpx 值得进候选，代价是源码 DSL 锁定。

**✅ 适合**

### 适合「一套代码打小程序 + H5 + App」

- **内容 / 导购 / 营销 / 活动 / CMS 驱动的页面。**视图以列表、卡片、详情、表单为主，交互密度低，UI 就是数据的函数。
- **交易链路中标准化的部分**：商品列表、详情、下单表单、订单与售后、个人中心、优惠券。
- **企业内部工具**：OA、审批、报表、巡检、CRM、考勤。这类正是 uni-app x 公开案例的主体，也是最能吃到「一套代码 + 一套自动化测试」红利的形态。
- **政务 / 民生服务**：查询、办事指南、预约、缴费。多入口需求天然强（小程序 + H5 + App + 鸿蒙）。
- **品牌官网 / 门店 / 会员 / 预约**，以及教育类的课程展示与轻互动。
- **IoT 的配套 App**（设备列表、状态、参数设置），前提是把蓝牙/配网封装成原生插件，UI 层跨端。

**⛔ 不适合**

### 绝对不适合

- **设备强交互**：蓝牙配网、NFC、USB/串口、外设收银。H5 在 iOS 上是**零可能**（WebKit 书面拒绝实现），小程序端各家能力也不齐。
- **后台常驻**：运动记录、导航、IM 保活、后台定位、常驻通知。iOS 的 H5 全线为零。
- **高帧率 / 高交互密度**：专业图形编辑、视频剪辑、富文本编辑器、游戏。移动端 INP 达标率在这类站点只有 56–63%。
- **音视频深度定制**：自研编解码、美颜滤镜链路、低延迟连麦。小程序原生组件的层级与同层渲染是硬约束，容器方案还要另接三方 SDK。
- **需要动态下发第三方代码到小程序**：`eval`/`new Function` 禁令是根本性的，没有绕法。
- **主包吃紧的重前端应用**：2M 是硬顶，且 Taro 的模板预绑属性、任何 wasm 都必须打进包内。
- **需要在 iOS 上可靠离线**：自家 App 的 WKWebView 没有 Service Worker；普通 Safari 标签页 7 天无交互即清空。
- **强依赖 RN / Flutter 既有原生生态**：这些生态无法跟着代码跨到小程序，第 07 节是结构性的，不是工程量问题。

### 一条实用的分层策略

不要在「全跨端」和「全原生」之间二选一。已被京东（Taro on Harmony 只负责原生页面渲染与桥接，路由/定位/权限由京东零售 mpass 团队原生提供）和 mPaaS（「稳态用原生、敏态用容器」）两边验证过的做法是：

- **骨架与能力层原生**：启动、路由、账号、支付、推送、音视频、设备能力、性能监控。
- **业务页面跨端**：列表、详情、表单、活动、内容页 —— 这是 80% 的页面数和 80% 的迭代量。
- **性能敏感页单独降级**：首页、商详、长列表可以在同一框架内走特殊路径（Taro 的鸿蒙长列表组件、uni-app x 的 list-view 复用 + flatten、微信的 Skyline 分包）。

### 本报告明确标注为不确定的项

1.  Taro 鸿蒙**多线程架构与 React C++ 化是否已 GA** —— 2025 年两篇官方博文称「试点接入 / 验证测试阶段」，但 4.1.0 与 4.2.0 release note 及 4.x 鸿蒙文档中均无落地痕迹，倾向未 GA。
2.  Taro 4.x 的 `compiler` **实际默认值** —— 文档仍写 `webpack4`，但该通道 4.x 无稳定制品。
3.  Taro 是否官方支持 **Svelte** —— 首页有 logo，`framework` 枚举无该值（按不可用判断）。
4.  uni-app x 对**支付宝小程序**的支持状态 —— 介绍页称已支持，同页路线图又列为 2026 待完成。
5.  **setData 单次 1024KB 上限** —— 在 2026 年现行微信官方文档中已找不到原文。
6.  微信官方是否给出**节点数上限建议** —— 只有定性建议，无数字。
7.  **Skyline 的布局引擎 / 自绘底座是否基于 Flutter** —— 官方文档未提及，社区说法无佐证。
8.  2025-10 微信社区帖的「Skyline 接入量同比 17 倍 / PV 4 倍 / 启动 -20% / 跳页 -50%」 —— 原帖需登录，仅取到搜索摘要。
9.  **kbone 是否已被微信官方废弃** / **Rax 是否有官方 deprecation 与继任者** —— 均无公告，只有 git 与 npm 停更的间接证据。
10. **滴滴 2026 年内部是否仍在用 Mpx** —— 无当年度官方声明。
11. **百度智能小程序的生态存续状态与包体积上限** —— 文档站为 SPA 空壳，多次抓取超时，未取到任何正文。
12. **支付宝小程序主包上限 2MB 还是 4MB** —— 官方两页自相矛盾。
13. **WKWebView 是否与 Safari 享有同等 JIT** —— 未能用官方来源证实。
14. **欧盟是否已有第三方浏览器引擎实际上架** —— 未取到确认或否认的官方来源。
15. **FinClip 桌面端是否支持 Linux**、iOS/鸿蒙/桌面端包体积、官网「自研 JavaScript 引擎」与文档「JSCore + 可选 J2V8」的口径冲突 —— 均需向厂商确认。
16. **mPaaS 与支付宝线上基础库的实际差距** —— opendocs 抓取失败，方向确定（mPaaS 停在 2.8.9）但无法量化。

### PoC 必测清单（因为官方全都不给数）

1.  各端集成后的 **APK / IPA / HAP 实测增量**，含全 ABI 的 .so 与你实际要用的每个扩展 SDK。
2.  冷启动 / 二次启动耗时、内存峰值、长列表 FPS —— 容器厂商与部分框架的官方文档零基准数据。
3.  Skyline：先跑通「关掉 AB 实验」的配置，否则线上根本没生效；再逐条对照第 06 节的 CSS / 组件限制清单跑一遍存量页面。
4.  鸿蒙端逐个验证你依赖的 API 与组件 —— 容器厂商都没有完整的鸿蒙差异清单。
5.  如果考虑 uni-app x 蒸汽模式：用 release 包测（debug 性能极差），并验证选项式 → 组合式、关系选择器 → BEM、样式隔离 2.0 三项改造的实际工作量。
